# ISO 21423 ISO Upstream Bridge Implementation Plan (Plan 5 of 5)

> **Execution order:** [Plan 4 — ISO Robots](2026-08-25-iso21423-iso-robots.md) ships **first** and has higher priority. The two are otherwise independent: separate ingest modules, separate `Iso21423Client`s on **separate brokers** (ORO's own for Plan 4; an upstream facility's for this one), separate `enabled` flags, opposite data directions. Plan 4 builds the three files both share (`sharedConfig.js`, `entityUuid.js`, `ccs.js`); this plan consumes them — see **Shared with Plan 4** below.

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build the ORO-side ISO 21423 bridge — a new `ingest` module that registers ORO robots as ISO 21423 IMRs under one IMRFM identity, republishes their telemetry into the ISO namespace in a facility CCS, serves `move`/`pauseImr`/`resumeImr`/`cancelRequest` requests by executing ORO Actions through the platform's own action framework, and drives its own broker-ACL provisioning — all disabled by default.

**Architecture:** The bridge is a duck-typed ingest module (`load(settings)` / `shutdown()` / `reportHealth()`, the `UpstreamModule` shape) that owns exactly one `FleetGateway` from `@openrobops/iso21423`. It reads the robot roster from the `robots` Mongo collection, taps normalized telemetry off the in-process `attributes` worker-queue exchange (the same seam `DerivedAttributesService` uses) and nowhere else, converts poses into the facility CCS with `/geometry`, and executes **every** command as an ORO ActionDefinition through the app's REST action endpoint — so ISO-originated commands are subject to the same operator locks, argument validation and audit logging as commands issued from the ORO UI. The gateway opens its **own** MQTT session to the same Mosquitto instance; ORO's `ros/*` topics and the SDK's `/ISO_21423/v1/*` topics never collide. One small piece lives in the Meteor app: a provisioner that turns the bridge's published roster into `mqtt_credentials` ACL grants.

**Tech Stack:** Plain-JS CommonJS-via-Babel (Flow-free), Node ≥22, `@openrobops/iso21423` (dual CJS/ESM, consumed through its CJS build), `mqtt@^5.15` (already an ingest dependency and the SDK's peer dep), `mongodb@^7`, `protobufjs@^8`, mocha + node `assert` + `sinon`.

**Spec:** [`docs/nodejs_design/docs/oro_integration.md`](../../nodejs_design/docs/oro_integration.md) **§2** is the binding spec for this plan (§1 for the compatibility constraints, §3 for distribution). Supporting: [`deliverables.md`](../../nodejs_design/docs/deliverables.md) (the `FleetBackend` seam sketch), [`example_imrfm.md`](../../nodejs_design/docs/example_imrfm.md) (the gateway usage walkthrough), [`nodejs_api.md`](../../nodejs_design/docs/nodejs_api.md) §13 (ND-15 security).

**Repo: the ORO repository** (`github.com/openrobops/oro`, local checkout `oro/`). **Every `src/…`, `test/…`, `settings.json` and `package.json` path in this plan is relative to `oro/ingest/`.** Paths that start with `app/`, `k8s/`, `terraform/` or `mqtt/` are relative to the ORO repo root. Most of the work is in `oro/ingest/`; Task 6 also adds one module and one test to the Meteor app in `oro/app/`. All `npm` commands run from `oro/ingest/`. **This plan document itself lives in the `iso21423` repo** (`docs/superpowers/plans/`) alongside Plans 1–4, because the plan argues from the SDK design docs; the code it describes does not.

## Global Constraints

- **Disabled by default.** The bridge only runs when `settings.iso21423.upstream.enabled === true`. Absent key ⇒ absent bridge, no MQTT session, no Mongo reads, no log noise beyond one INFO line. Default rendered config writes `{"enabled": false}` (Task 8, terraform).
- **Settings live under `settings.iso21423.upstream`.** `settings.iso21423` itself holds only the facility-level keys both ISO directions share — `uuidNamespace`, `ccs` (the calibration), `logging`. Everything else, **including `broker`**, is under its own subtree (`iso21423.robots` for Plan 4, `iso21423.upstream` here). The bridge never reads `iso21423.robots`.
- **A different broker from Plan 4's, and an explicit one.** This direction connects **out** to an upstream, facility-owned ISO broker, so `settings.iso21423.upstream.broker` is required and is **never** defaulted to ORO's own broker (Plan 4's decision 13). Pointing it at ORO's own broker is legal for a co-located facility, in which case ORO appears there as two IMRFM entities — one per direction — which is correct.
- **Its own MQTT session and its own `Iso21423Client`, never ingest's and never Plan 4's.** The gateway gets its own `mqtt` client (via the SDK's `createMqttTransport`) with its own `clientId`, its own credential from `settings.iso21423.upstream.mqtt`, and `cleanSession: false` + LWT semantics the SDK requires. There is no shared client between the two directions, by design. The bridge must never call `OroMqtt.registerListener` for ISO topics and must never publish ISO topics through `OroMqtt`. `OroMqtt` is used **only** to publish ORO robot commands on `r/<robotId>/…` (Task 5).
- **Plain-JS CommonJS via Babel.** No TypeScript toolchain, no build step for the bridge. Use JSDoc `@typedef`/`@param`/`@returns` where a shape is non-obvious. No Flow annotations in new files (new ingest code does not add them).
- **No new runtime dependencies beyond the SDK.** Everything else comes from `lodash`, `mongodb`, `mqtt`, `protobufjs`, `axios`, `moment` and `node:crypto`, all already present. Do not add `uuid` — Task 2 derives UUIDs with `node:crypto`.
- **`src/shared/` is generated, not edited.** `ingest/src/shared/constants.js` (and `attributes.js`, `oro.proto`, …) are copies of the app's, mirrored by `ingest/import.sh`. The one new collection name (Task 6) is added to `app/imports/shared/constants.js` and imported across — never edited in `ingest/src/shared/` directly.
- **The bridge never writes to `mqtt_credentials`.** It publishes a roster-state document; the Meteor app owns every credential write (Task 6).
- **The Meteor app must be up for the bridge to execute any ISO action.** Every command — `move`, `pauseImr`, `resumeImr` — goes through the app's REST action endpoint (pinned decision 8), so the app is a hard runtime dependency of the ISO command path. Telemetry, registration and ACL publishing are unaffected and keep working while the app is down. When the endpoint is unreachable the bridge answers `GENERAL_FAILURE`, emits an `oro-actions-unreachable` diagnostic, and `reportHealth()` reports `actions: 'unreachable'` — it never crashes and never silently degrades to a direct MQTT publish.
- **The SDK stays optional and lazily loaded.** `require`/static `import` of `@openrobops/iso21423` at module top level would make a missing optional dependency a boot failure. Load it with `await import('@openrobops/iso21423')` **inside** `load()`, inside a `try`/`catch`, exactly where `main.js:174-182` does today.
- **Lifecycle integrated with ingest's.** `load(settings)` is called from `run()` in `src/main.js`; `shutdown()` is called from `shutdown()` in `src/main.js` (which today calls a non-existent `iso21423.shutdown()` at `main.js:200` — Task 1 fixes that). Neither may throw: a bridge failure must never prevent ingest from serving or shutting down.
- **Topic coexistence.** The ISO namespace is exactly `/ISO_21423/v1` (leading slash) and is disjoint from ORO's `r/<robotId>/…` and `system/…` topics on the same Mosquitto instance (`oro_integration.md` §1). Never publish an ISO payload under `r/…` or an ORO payload under `/ISO_21423/…`.
- **ORO robot ids are not UUIDs.** `robots._id` is an operator-chosen string (`app/imports/lib/collections.js:36-67`). Every ISO entity uuid is derived deterministically (Task 2) — never generated randomly, never persisted.
- **Comment convention (mandated).** Mirror the SDK's `ts-sdk/README.md` "Code style" rule in JSDoc form: *every non-trivial exported class, function and method carries a `/** … */` comment stating what the signature alone can't — units, ordering, throw conditions, side effects.* Trivial one-line delegations stay bare. Spec references (`ND-15`, `D-11`, ISO clause numbers, `oro_integration.md §2`) are kept verbatim wherever they apply.
- **Conventional commits** for every commit (`feat:`, `fix:`, `test:`, `docs:`, `chore:`).
- **Tests** are mocha files in `test/`, named `test/iso21423-*.test.js`, using node `assert` (the style of `test/upstream.test.js`). Run with `npm run test:unit`; target one file with `npm run test:unit -- --grep "<name>"`. `test/it-helper.js` boots a `mongo-unit` Mongo and initializes the `MongoManager` singleton for every test file — real Mongo is available in tests, no Mongo mocking needed.

## Design decisions this plan pins

These are binding for every task below. Decisions marked **[HUMAN-DECIDED]** were reviewed and settled by the project owner on 2026-08-25 — an executor must implement them as written and **must not re-decide them**, even if a simpler or more "correct" alternative suggests itself. The rest were pinned by the plan author against silent or contradictory docs (see the review notes).

1. **[HUMAN-DECIDED] Telemetry comes from ORO attributes and ONLY from ORO attributes — no protobuf or MQTT sniffing, ever.** ORO's per-robot MQTT payloads do **not** carry battery at all — `src/shared/oro.proto:62-63` records that the battery fields were removed, and battery reaches ORO only as generic key-values on `r/+/custom` resolved per-robot into the `batteryPercentage` / `batteryVoltage` / `batteryIsCharging` attributes (`src/server/modules/customData.js:96` → `src/server/attributes.js:461`). The one place where pose, online-state, speed **and** battery all exist already normalized is `AttributesManager._cascadeUpdates` (`src/server/attributes.js:363`), which publishes `oro.system.AttributesUpdate` to the `attributes` direct exchange with routing key `update-values` (`src/server/attributes.js:377-381`, `src/server/queues/messageQueue.js:266`). `InMemoryWorkerQueues.doSend` fans out to **every** queue bound to that exchange+key (`src/server/queues/memoryWorkerQueue.js:86-104`), so the bridge binds its own queue alongside `derived-attributes` without displacing it.

   **The attributes exchange is the bridge's permanent and only telemetry input.** Do not add a `registerListener('ros/loc/pose', …)` or `ros/odometry/data` tap, not for odometry rate, not for anything: registering `ros/odometry/data` would silently disable the built-in speed/distance processing at `src/server/mqtt.js:522-644` (that branch is an `else if` after the `_listeners` check at `:494`), and a second input path would mean two sources of truth for the same pose. The accepted cost is that odometry arrives at ORO's attribute-write rate (pose is rate-limited to ~1 Hz by default, `src/server/modules/localization.js:97-99`), not at ISO's 30 Hz ceiling. If a deployment needs faster ISO odometry, the fix is to raise ORO's pose attribute rate, not to add a tap.

   The corollary is the **ISO attribute-source convention**: every ORO attribute id the bridge reads is named in `DEFAULT_ATTRIBUTE_SOURCES` (`src/server/iso21423/config.js`) and is overridable per deployment via `settings.iso21423.upstream.attributeSources`. A deployment whose pose attribute is called something else changes one setting; the bridge code never hardcodes an id outside that table.
2. **Entity UUIDs are RFC 4122 v5, derived from the ORO id.** `uuidV5(robotId, namespaceUuid)` with the namespace taken from the shared `settings.iso21423.uuidNamespace`, computed in ~20 lines with `node:crypto`'s SHA-1 (Task 2). Deterministic across restarts and across a fleet-manager restart, so retained ISO topics stay addressed to the same entity; nothing is written to Mongo. The IMRFM's own uuid is `settings.iso21423.upstream.imrfmId` (explicit, because it is the identity operators put in ACLs and dashboards).
3. **Roster source and refresh = poll + diff on the `robots` collection.** `robots` (`COLLECTIONS.ROBOTS`, `src/shared/constants.js:23`) is read every `rosterPollMs` (default 30000) and diffed against the registered set. A Mongo change stream was rejected: it requires a replica set, and `mongo-unit` in `test/it-helper.js` gives a standalone `mongod`, so change streams would make the whole feature untestable in ingest's suite.
4. **[HUMAN-DECIDED] Fleet selection is opt-in by explicit list.** `settings.iso21423.upstream.fleet = { mode: 'list' | 'all', ids: [] }`, default `{ mode: 'list', ids: [] }` — enabling the bridge without naming robots bridges **nothing**. ORO has no tag or label field on robot documents (the schema at `app/imports/lib/collections.js:36-67` has no `tags`; the undeclared `collections` array read at `src/server/model/robot.js:97` is the only fleet-subset-ish field), so a tag-based selector cannot be built today. `mode: 'all'` is provided for single-facility deployments. A `TODO(oro-tags):` marker sits at the selector in `config.js` (Task 1) and at the query builder in `roster.js` (Task 2): when ORO grows robot tags — a separate ORO ticket — adding `mode: 'tagged'` is one branch in each spot and nothing else in the bridge changes.
5. **CCS reference points live in `settings.json`, not Mongo.** `oro_integration.md` §2 says both ("stored in Mongo settings" in the CCS bullet, "ingest's `settings.json` (bridge UUID, CCS reference points, broker credentials)" in the Configuration bullet). `settings.json` wins: ORO has **no** settings/config collection at all, and the one modelled Mongo home for facility frames — `spatial_transformations` (`app/imports/lib/collections.js:808-828`) — has zero live readers or writers today (every consumer is commented out, e.g. `app/imports/server/actions.js:1558`). Task 4 isolates the loader behind one function so moving to `spatial_transformations` later is a one-file change.
6. **Fewer than 3 reference points ⇒ the bridge runs with CCS conversion disabled.** `fitTransform` requires ≥3 pairs (`ts-sdk/src/geometry/transform.ts:16-18`). Rather than refusing to start, the bridge emits one `console.warn` naming the count, publishes status and battery normally, and **suppresses odometry entirely** — publishing a pose in the wrong frame under a `ccsId` that claims otherwise is worse than publishing none. `reportHealth()` reports `ccs: 'uncalibrated'`.
7. **[HUMAN-DECIDED — interim] ORO has no mode concept yet ⇒ every online status carries `MODE_AUTO` first.** ISO puts the mutually-exclusive `MODE_*` marker first in `states` (`ts-sdk/src/types/status.ts:9`). ORO's robot document has no teleop/manual/maintenance flag today, so `MODE_AUTO` is the honest constant except when the robot is offline (`['OFFLINE']` alone). **Operating modes are coming to ORO.** A `TODO(oro-modes):` marker sits at the exact line in `mapStatus` (Task 3) where the future ORO mode value maps onto the ISO `MODE_*` set; the rest of the state table is unaffected because the mode slot is already separate from the motion slot. The rest of the table (`PAUSED` > `CHARGING` > motion > `IDLE`, the 0.02 dead-band, `LEFT_TURN`/`RIGHT_TURN` for in-place rotation, and no `LOST`-on-stale-pose) is **[HUMAN-DECIDED]** as drafted.
8. **[HUMAN-DECIDED] EVERY ISO command runs as an ORO Action through the app's REST endpoint. There is no direct `r/<robotId>/…` publish anywhere in the bridge.** One ingress: `POST {peerClient.url}/api/robots/<robotId>/actions`, header `x-auth-peer-key`, body `{ actionId, parameters }` (`app/imports/server/rest/actions.js:68`, `:191-197`; `app/imports/server/rest_api.js:197`, `:205-208`). Per ISO action type:
   - **`move`** → the auto-seeded `NavigateTo-000000` (`app/imports/shared/actions.js:175-197`), `parameters: { pose: { x, y, theta } }` in the ORO map frame, `frameId` deliberately omitted (ORO drops it on the wire — `app/imports/server/modules/nav2d.js:82-95`).
   - **`pauseImr`/`resumeImr`, `pause.strategy: 'action'` (default)** → the deployment's own `pauseRobot` / `resumeRobot` ActionDefinitions, realized per-robot however the deployment chooses (ROS topic, bash script, anything the framework supports). Missing ⇒ `ACTION_NOT_IMPLEMENTED` plus one actionable log line.
   - **`pause.strategy: 'navGoal'`** → ORO's auto-seeded `CancelNavGoal-000000` (`app/imports/shared/actions.js:198-210`) to stop and the move action to resume. **This is no longer a bypass**: `CancelNavGoal` publishes exactly the `ros/nav/goal_to_current_pose` the original draft published by hand (`nav2d.js:59-71`), so routing it through the framework costs nothing and keeps locks and audit. It stops *navigation only*, which is why `'action'` remains the default.
   - **`cancelRequest` / an aborted or timed-out `move`** → `CancelNavGoal-000000`. The Actions framework has **no** per-execution cancel — no REST route, no Meteor method (`app/imports/server/actions.js:88-91`), and `executionId` exists only for `RunScript` (`actions.js:1019-1022`). An override goal at the robot's current pose is the honest equivalent, and it is what ORO's own UI uses.
9. **[HUMAN-DECIDED] ISO-originated commands are subject to ORO's operator locks, and ORO writes their audit log.** This replaces the earlier bypass. The peer key resolves to the system user (`app/imports/shared/roles.js:71-89`), which short-circuits the *permission* gates (`app/imports/server/lock.js:396`, `:413`) but **not** the lock check: the branch at `lock.js:430` has no system-user guard and `:437` compares `robotLock.userId != userId`, so a robot locked by a human operator refuses an ISO command with `{ error: 'Robot is locked by <name>' }`. Every action the bridge runs carries `lock: true` in its template (`app/imports/shared/actions.js:180`, `:203`; the field is `ACTION_FIELD_RESTRICTED`, `lock.js:44`, schema `app/imports/lib/actions.js:48`). ORO also logs the outcomes itself: successes via `EventLog.logExecutedAction` (`app/imports/server/actions.js:1316`), refusals via `_logActionFailure` (`lock.js:359-376`), unknown ids via `rest/actions.js:78-91`. **Caveat to document, not an ISO-specific hole:** locking engages only when the tenant's lock preference is `automatic` or `explicit`; the default is `disabled` (`app/imports/lib/lock.js:24-42`), in which case nobody is locking anything, the UI included.
10. **[HUMAN-DECIDED] The bridge never touches `mqtt_credentials`. It publishes a roster-state document; the Meteor app provisions the ACLs from it.** Split of responsibility (Task 6):
    - **Bridge (ingest):** maintains one document in a new `iso21423_roster` collection — the single source of truth for the UUID derivation, since the IMR uuids are derived (pinned decision 2) and exist nowhere else. Written on every roster change.
    - **App (Meteor):** a new `app/imports/server/iso21423AclProvisioner.js`, sibling to `app/imports/server/mqttCredentialProvisioner.js`, observes that collection and maintains the bridge credential's `acls` array. Started from `app/server/main.js:110`, right after `seedMasterCredentials()`.
    This resolves `oro_integration.md` §2's "re-provisioning as the fleet changes can be automated **by the app**" literally, and keeps password hashing (`app/imports/server/mqttCredentialUtils.js:38-44`) and every `mqtt_credentials` write on the side that already owns them. Credential *creation* stays out of scope on both sides — the app-side provisioner updates an existing document and logs an actionable warning when it is missing, and ND-15's self-check surfaces any remaining gap at connect time.
11. **ACL grants are emitted as one entry per access bit, not an OR'd bitmask.** `app/imports/server/mqttCredentialProvisioner.js:112-115` documents verbatim that "MOSQ_ACL_* appear to be bitmasks, but combining them does not work", and duplicates entries for subscribe+read — while the per-robot path at `:71` does OR read|write into `acc: 3`. The two disagree; the app-side provisioner takes the safe superset and emits three entries per topic (`acc: 1` read, `acc: 2` write, `acc: 4` subscribe).
12. **[HUMAN-DECIDED] The bridge audit-logs only what ORO cannot: the requests it rejects before submitting an action.** Decision 9 means ORO logs every command the bridge hands it, so a bridge-side line for those would double every row in the audit widget. What ORO never sees — a malformed `move`, a foreign `ccsId`, an uncalibrated CCS, an entity that maps to no robot, a missing ActionDefinition — the bridge records itself as an `action.failed` `event_log` document mirroring `LockManager._logActionFailure` (`app/imports/server/lock.js:361-371`), written directly from ingest as `UpstreamModule` already does (`src/server/modules/upstream.js:964-1006`), with the same configurable-actor trick (`userId: 'iso21423'`, `userName` from `audit.actorName`; the UI shows `userName || userEmail || userId`, `app/imports/lib/events.js:387-390`). Task 5c.
13. **[HUMAN-DECIDED] `move` completes on arrival, not on submission.** Confirmed necessary: the REST call returns `{ status: 'started', startTs, lastUpdateTs }` (`app/imports/server/rest/actions.js:117-127`) — a hardcoded submission ack — and `NavigateTo` produces no `executionId` at all, so the status route 404s with *"only status for actions of type RunScript is implemented"* (`rest/actions.js:143`, backed by `RobotCustomScript`, `app/imports/lib/collections.js:482-518`). There is no completion feedback for navigation anywhere in ORO. `moveCompletion: 'arrival'` (default) therefore watches the pose converge inside `toleranceRadius` and times out otherwise; `'ack'` is the opt-out that resolves on submission. Task 5b.
14. **[HUMAN-DECIDED] Deployment prerequisites are reported, never enforced.** ISO integration needs per-deployment setup that lives outside `settings.json`: the `pauseRobot`/`resumeRobot` ActionDefinitions, and the ORO attributes named by `attributeSources`. The bridge checks what it can at startup, logs one actionable line per gap and exposes them through `reportHealth()` — and starts anyway, rejecting only the affected ISO requests. No bootstrap file ships: required actions depend on each robot's implementation, so they are deployment setup, never a seeded default. Task 5d, documented in Task 8's "Deployment prerequisites".

```javascript
/**
 * Settings validation for the ISO 21423 Upstream bridge (`settings.iso21423.upstream`, plus the
 * shared `settings.iso21423` keys both ISO directions use).
 *
 * Pure: no I/O, no Mongo, no logging — so it is trivially unit-testable, following the
 * convention of `app/imports/server/settingsValidation.js`. Reports ALL problems in one
 * pass so an operator can fix them together.
 *
 * Scope: this validates the SETTINGS FILE only. The other half of getting the bridge working is
 * the deployment's own setup — the `pauseRobot`/`resumeRobot` ActionDefinitions and the ORO
 * attributes named by `attributeSources` — which lives in Mongo and in each robot's integration,
 * not here. Those are checked at startup by `prerequisites.js` (Task 5d) and reported through
 * `reportHealth()`; they never block the bridge from starting. See the "Deployment prerequisites"
 * section of `docs/iso21423-bridge.md`.
 */

// Shared with the ISO Robots direction; `sharedConfig.js` is built by Plan 4, Task 1.
// `parseShared` owns the FACILITY-level keys both directions read — `uuidNamespace`, `ccs` and
// `logging` — returning them validated and defaulted. It deliberately does NOT own the broker:
// the two directions talk to two different brokers (Plan 4's decision 13).
import { parseShared, UUID_RE, DEFAULT_ATTRIBUTE_SOURCES } from './sharedConfig';

const FLEET_MODES = ['list', 'all'];

const MOVE_COMPLETION_MODES = ['arrival', 'ack'];

const PAUSE_STRATEGIES = ['action', 'navGoal'];

/**
 * The ISO attribute-source convention (human decision 7): the ORO attribute ids the bridge
 * reads for every ISO resource it publishes. Overridable per deployment via
 * `settings.iso21423.upstream.attributeSources` — a deployment that names its pose attribute
 * `poseFused` changes one setting instead of patching the bridge.
 *
 * Values are the real ORO attribute ids from `src/shared/attributes.js:39-60`.
 */
const DEFAULT_ATTRIBUTE_SOURCES = {
  online: 'agentOnline',
  pose: 'pose',
  speedLinear: 'speedLinear',
  speedAngular: 'speedAngular',
  batteryPercentage: 'batteryPercentage',
  batteryVoltage: 'batteryVoltage',
  batteryIsCharging: 'batteryIsCharging',
};

/**
 * @typedef {Object} Iso21423Config Resolved, defaulted bridge configuration.
 */

/**
 * Validates and defaults the `settings.iso21423` block, returning the resolved UPSTREAM config
 * with the shared keys merged in.
 *
 * @param {Object|undefined} raw the `iso21423` key from settings.json, possibly absent
 * @returns {{ config: Iso21423Config|null, errors: string[] }} `config` is null when the
 *   bridge is disabled or absent (with an empty `errors`), or when validation failed
 *   (with a non-empty `errors`). Never throws.
 */
const validateConfig = (raw) => {
  // `raw` is the whole `settings.iso21423` block: the facility-level keys plus one subtree per
  // direction. This direction's broker is somebody else's, so it is explicit and never defaulted
  // (Plan 4's decision 13).
  const up = (raw && raw.upstream) || {};
  if (up.enabled !== true) {
    return { config: null, errors: [] };
  }
  const errors = [];
  const requireUuid = (value, name) => {
    if (typeof value !== 'string' || !UUID_RE.test(value)) {
      errors.push(`iso21423.${name} must be a UUID string (got ${JSON.stringify(value)})`);
      return null;
    }
    return value.toLowerCase();
  };

  // Shared keys. `parseShared` (sharedConfig.js, built by Plan 4) owns the ones both directions
  // read; anything upstream-only stays here.
  const { shared, errors: sharedErrors } = parseShared(raw);
  errors.push(...sharedErrors);

  const imrfmId = requireUuid(up.imrfmId, 'upstream.imrfmId');

  // This direction connects OUT to an upstream, facility-owned ISO broker, so the endpoint is
  // always explicit — there is nothing sensible to default it to (Plan 4's decision 13). The
  // credential is this direction's own, as always.
  const broker = { url: undefined, tls: {}, ...(up.broker || {}) };
  const mqtt = { ...broker, ...(up.mqtt || {}) };
  if (typeof mqtt.url !== 'string' || !mqtt.url) {
    errors.push('iso21423.upstream.broker.url is required — the upstream facility\'s ISO broker '
      + '(e.g. "mqtts://facility-broker:8883"). It is never defaulted to ORO\'s own broker.');
  }

  // TODO(oro-tags): a tag-based fleet selector (`mode: 'tagged', tags: [...]`) becomes possible
  // once ORO grows robot tags. The `robots` documents have no tags/labels field today
  // (`app/imports/lib/collections.js:36-67`), so 'list' and 'all' are the only honest modes.
  // Tracked as a separate ORO ticket; when it lands, add the mode here and one branch in
  // `RobotRoster.refresh`'s query builder — nothing else in the bridge changes.
  const fleet = { mode: 'list', ids: [], ...(up.fleet || {}) };
  if (!FLEET_MODES.includes(fleet.mode)) {
    errors.push(`iso21423.upstream.fleet.mode must be one of ${FLEET_MODES.join('|')}`);
  }
  if (!Array.isArray(fleet.ids)) {
    errors.push('iso21423.upstream.fleet.ids must be an array of ORO robot ids');
  }

  const moveCompletion = up.moveCompletion || 'arrival';
  if (!MOVE_COMPLETION_MODES.includes(moveCompletion)) {
    errors.push(`iso21423.upstream.moveCompletion must be one of ${MOVE_COMPLETION_MODES.join('|')}`);
  }

  const pause = {
    strategy: 'action', pauseActionId: 'pauseRobot', resumeActionId: 'resumeRobot',
    ...(up.pause || {}),
  };
  if (!PAUSE_STRATEGIES.includes(pause.strategy)) {
    errors.push(`iso21423.upstream.pause.strategy must be one of ${PAUSE_STRATEGIES.join('|')}`);
  }

  if (errors.length) {
    return { config: null, errors };
  }

  return {
    config: {
      enabled: true,
      imrfmId,
      // ---- shared ----
      uuidNamespace: shared.uuidNamespace,
      ccs: shared.ccs,
      logging: shared.logging,
      // ---- upstream-only ----
      manufacturerName: up.manufacturerName || 'OpenRobOps',
      mqtt: {
        url: mqtt.url,
        username: mqtt.username,
        password: mqtt.password,
        tls: mqtt.tls || {},
        clientId: mqtt.clientId,
      },
      fleet,
      lowBatteryPercent: Number.isFinite(up.lowBatteryPercent) ? up.lowBatteryPercent : 20,
      rosterPollMs: Number.isFinite(up.rosterPollMs) ? up.rosterPollMs : 30000,
      selfCheck: up.selfCheck !== false,
      attributeSources: { ...DEFAULT_ATTRIBUTE_SOURCES, ...(up.attributeSources || {}) },
      moveCompletion,
      moveArrival: {
        timeoutMs: 120000, pollMs: 500, defaultToleranceRadius: 0.5, ...(up.moveArrival || {}),
      },
      // ORO auto-seeds both of these (`app/imports/server/actions.js:131-157`); overridable for
      // deployments that define their own navigation actions.
      moveActionId: up.moveActionId || 'NavigateTo-000000',
      cancelNavActionId: up.cancelNavActionId || 'CancelNavGoal-000000',
      pause,
      audit: { enabled: true, actorName: 'ISO 21423 bridge', ...(up.audit || {}) },
      rosterStateId: up.rosterStateId || 'iso21423-bridge',
    },
    errors: [],
  };
};

export { validateConfig, FLEET_MODES };
```

```javascript
// src/server/iso21423/index.js  (Apache-2.0 header as in Step 3, omitted here for brevity —
//  copy the 15-line header verbatim from any existing ingest source file)

/**
 * ISO 21423 bridge module (`oro_integration.md` §2).
 *
 * Registers ORO robots as ISO 21423 IMRs under one IMRFM identity, republishes their
 * telemetry into the `/ISO_21423/v1` namespace, and serves inbound requests by driving
 * ORO's existing MQTT command path.
 *
 * Disabled by default: `load()` returns immediately unless `settings.enabled === true`.
 * The SDK is an OPTIONAL dependency and is therefore imported dynamically inside `load()`
 * — a static import would turn a missing package into an ingest boot failure.
 */
import { validateConfig } from './config';

class Iso21423BridgeModule {
  /**
   * @param {Object} deps
   * @param {Object} deps.mongo   the MongoManager singleton (src/mongo.js)
   * @param {Object} deps.mqtt    the OroMqtt singleton (src/server/mqtt.js), used ONLY to
   *                              publish ORO robot commands on `r/<robotId>/…` — never for
   *                              ISO topics, which travel on the bridge's own session
   * @param {Object} deps.workerQueue the InMemoryWorkerQueues instance, for the telemetry tap
   */
  constructor({ mongo, mqtt, workerQueue }) {
    this._mongo = mongo;
    this._oroMqtt = mqtt;
    this._workerQueue = workerQueue;
    this._config = null;
    this._sdk = null;
    this._gateway = null;
  }

  /**
   * Validates settings, loads the SDK, and connects the gateway. Never throws: every failure
   * path logs and leaves the bridge inert so ingest keeps serving.
   *
   * @param {Object|undefined} settings the `iso21423` block of settings.json
   * @returns {Promise<this>}
   */
  load = async (settings) => {
    const { config, errors } = validateConfig(settings);
    if (errors.length) {
      console.error('ISO 21423 bridge is misconfigured and will not start:');
      errors.forEach((e) => console.error('  - ' + e));
      return this;
    }
    if (!config) {
      console.log('ISO 21423 bridge is OFF');
      return this;
    }
    this._config = config;

    try {
      this._sdk = await import('@openrobops/iso21423');
    } catch (err) {
      console.error('ISO 21423 bridge cannot start: @openrobops/iso21423 is not installed:', err.message);
      this._config = null;
      return this;
    }

    try {
      const { FleetGateway, createMqttTransport } = this._sdk;
      this._gateway = await FleetGateway.connect({
        transport: createMqttTransport(config.mqtt.url, {
          username: config.mqtt.username,
          password: config.mqtt.password,
          tls: config.mqtt.tls,
          reconnectPeriod: 5000,
        }),
        security: { selfCheck: config.selfCheck },
        imrfm: {
          id: config.imrfmId,
          manufacturerName: config.manufacturerName,
          details: { platform: 'OpenRobOps', service: 'ingest' },
          accepts: [],
          provides: [],
        },
      });
      this._gateway.client.on('error', (err) => console.warn('ISO 21423 client error:', err.message));
      this._gateway.client.on('diagnostic', (d) => config.logging && console.log('ISO 21423 diagnostic:', d));
      console.log(`ISO 21423 bridge is ON: IMRFM ${config.imrfmId} at ${config.mqtt.url}`);
    } catch (err) {
      console.error('ISO 21423 bridge failed to connect:', err.message);
      this._gateway = null;
    }
    return this;
  };

  /** Closes the gateway (and therefore its MQTT session). Safe to call when the bridge never started. */
  shutdown = async () => {
    if (!this._gateway) return;
    try {
      await this._gateway.close({ timeout: 5000 });
    } catch (err) {
      console.warn('ISO 21423 bridge shutdown error:', err.message);
    }
    this._gateway = null;
  };

  /** Health snapshot in the shape `UpstreamModule.reportHealth` uses (src/server/modules/upstream.js:253). */
  reportHealth = async () => {
```

```javascript
// (Apache-2.0 header)

/**
 * Fleet roster for the ISO 21423 bridge: turns the ORO `robots` collection into
 * `registerImr`/`unregisterImr` calls (`oro_integration.md` §2, "robot identity/registration
 * from Mongo robot documents").
 *
 * Refresh is a poll-and-diff rather than a Mongo change stream: change streams need a
 * replica set, and ingest's test harness (`test/it-helper.js`) runs a standalone `mongod`.
 */

/** ORO robot-document fields carried into the ISO IMR identity `details`. */
const IDENTITY_FIELDS = {
  name: 'robotName',
  hostname: 'hostname',
  version: 'agentVersion',
  variant: 'variant',
};

class RobotRoster {
  /**
   * @param {Object} opts
   * @param {Object} opts.collection the `robots` Mongo collection
   * @param {{mode: 'list'|'all', ids?: string[]}} opts.selector which robots to bridge
   * @param {number} [opts.pollMs=30000] refresh interval
   * @param {(robotId: string, details: Object) => Promise<void>} opts.onAdd
   * @param {(robotId: string) => Promise<void>} opts.onRemove
   * @param {boolean} [opts.logging=false]
   */
  constructor({ collection, selector, pollMs = 30000, onAdd, onRemove, logging = false }) {
    this._coll = collection;
    this._selector = selector;
    this._pollMs = pollMs;
    this._onAdd = onAdd;
    this._onRemove = onRemove;
    this._logging = logging;
    this._registered = new Set();
    this._timer = null;
  }

  /** Runs one refresh, then polls every `pollMs`. The timer is unref'd so it never holds the process open. */
  start = async () => {
    await this.refresh();
    this._timer = setInterval(() => {
      this.refresh().catch((err) => console.warn('ISO 21423 roster refresh failed:', err.message));
    }, this._pollMs);
    if (this._timer.unref) this._timer.unref();
  };

  /** Stops polling. Registered robots are left registered — unregistering a whole fleet on a
   *  service restart would erase its retained ISO state (see FleetGateway.close's rationale). */
  stop = () => {
    if (this._timer) clearInterval(this._timer);
    this._timer = null;
  };

  /**
   * One diff pass: registers robots newly in scope and unregisters ones that left.
   *
   * A failing `onAdd` (e.g. the SDK's ND-15 self-check rejecting an un-ACL'd robot) is logged
   * and the robot is NOT marked registered, so the next pass retries it once the ACL lands.
   *
   * @returns {Promise<{added: string[], removed: string[]}>} what actually changed
   */
  refresh = async () => {
    // TODO(oro-tags): when ORO grows robot tags, add `mode: 'tagged'` here as
    // `{ tags: { $in: this._selector.tags } }` (plus the mode in config.js's FLEET_MODES).
    // Nothing else in the bridge changes — this query is the only place fleet membership is decided.
    const query = this._selector.mode === 'all'
      ? {}
      : { _id: { $in: this._selector.ids || [] } };
    const docs = await this._coll.find(query).toArray();
    const wanted = new Map(docs.map((d) => [d._id, this._detailsOf(d)]));

    const added = [];
    const removed = [];

    for (const [robotId, details] of wanted) {
      if (this._registered.has(robotId)) continue;
      try {
        await this._onAdd(robotId, details);
        this._registered.add(robotId);
        added.push(robotId);
      } catch (err) {
        console.warn(`ISO 21423 roster: failed to register robot ${robotId}: ${err.message}`);
      }
    }

    for (const robotId of [...this._registered]) {
      if (wanted.has(robotId)) continue;
      try {
        await this._onRemove(robotId);
      } catch (err) {
        console.warn(`ISO 21423 roster: failed to unregister robot ${robotId}: ${err.message}`);
      }
      this._registered.delete(robotId);
      removed.push(robotId);
    }

    if (this._logging && (added.length || removed.length)) {
      console.log(`ISO 21423 roster: +${added.length} -${removed.length}`);
    }
    return { added, removed };
  };

  /** Currently registered ORO robot ids. */
  registeredIds = () => [...this._registered];

  _detailsOf = (doc) => {
    const details = { oroRobotId: doc._id };
    for (const [oroField, isoField] of Object.entries(IDENTITY_FIELDS)) {
      if (doc[oroField] !== undefined) details[isoField] = doc[oroField];
    }
    return details;
  };
}

export { RobotRoster, IDENTITY_FIELDS };
```

**The ORO → ISO 21423 state mapping table (pinned decision 7, [HUMAN-DECIDED]).** Inputs are ORO
attribute values read through `config.attributeSources` (never a hardcoded id — pinned decision 1);
`paused` is the bridge's own per-robot flag, set by `pauseImr` in Task 5. Rows are evaluated
top-down; the first match wins for the motion slot.

**The mode slot** is the first element and is currently the constant `MODE_AUTO`:

> `TODO(oro-modes):` ORO is growing an operating-mode concept. When the robot document (or an
> attribute) carries a mode, map it here — `MODE_TELEOP` when a teleop session owns the robot,
> `MODE_MANUAL` when a local operator does, `MODE_MAINTENANCE` when the robot is out of service,
> `MODE_SEMIAUTO` for supervised autonomy, `MODE_AUTO` otherwise — and add its attribute id to
> `DEFAULT_ATTRIBUTE_SOURCES` as `mode`. Only the `MODE_AUTO` constant in `mapStatus` changes;
> the motion and battery slots below are independent of it. Until then `MODE_AUTO` is the only
> honest value: claiming a mode ORO cannot observe would be worse than claiming the common one.

Conditions below name the **canonical** state keys, which `TelemetryTap` produces by translating
incoming ORO attribute ids through `config.attributeSources` — so `mapStatus` itself never sees an
ORO attribute id.

| Canonical condition | ISO `states` |
| --- | --- |
| `online === false` | `['OFFLINE']` (nothing else appended) |
| `paused` flag set | `['MODE_AUTO', 'PAUSED']` |
| `batteryIsCharging === true` | `['MODE_AUTO', 'CHARGING']` |
| `speedLinear > +0.02` | `['MODE_AUTO', 'FORWARD']` |
| `speedLinear < -0.02` | `['MODE_AUTO', 'REVERSE']` |
| `speedAngular > +0.02` | `['MODE_AUTO', 'LEFT_TURN']` |
| `speedAngular < -0.02` | `['MODE_AUTO', 'RIGHT_TURN']` |
| otherwise | `['MODE_AUTO', 'IDLE']` |
| **appended** when `batteryPercentage < lowBatteryPercent` and the robot is online | `… , 'LOW_BATTERY'` |

`MODE_AUTO` is unconditional for an online robot because ORO models no operating mode *yet* (see
the `TODO(oro-modes):` above). `0.02` is the dead-band in ORO's units (m/s, rad/s) — below it the
robot is reporting sensor noise, not motion.

**Attribute ids are never hardcoded.** `mapStatus` and `TelemetryTap` take a `sources` object
(`config.attributeSources`) and read `state[sources.online]`, `state[sources.pose]` and so on. The
defaults in `DEFAULT_ATTRIBUTE_SOURCES` are the real ORO ids (`src/shared/attributes.js:39-60`:
`agentOnline`, `pose`, `speedLinear`, `speedAngular`, `batteryPercentage`, `batteryVoltage`,
`batteryIsCharging`); a deployment that names any of them differently overrides just that key.

```javascript
// (Apache-2.0 header)

/**
 * Telemetry tap: ORO robot attributes → ISO 21423 status/odometry/battery
 * (`oro_integration.md` §2, "status/odometry/battery from ingest's telemetry pipeline").
 *
 * The tap binds its own queue to the in-process `attributes` exchange, the same seam
 * `DerivedAttributesService` uses (`src/services/derivedAttributes/svcDerivedAttributes.js:84-98`)
 * and the one place where pose, online state, speed AND battery all exist already normalized
 * (`src/server/attributes.js:377-381`). ORO's MQTT protobufs carry no battery at all —
 * `src/shared/oro.proto:62-63` records that those fields were removed — so an MQTT tap could
 * not satisfy the spec.
 *
 * This is the bridge's ONLY telemetry input, permanently (pinned decision 1): no protobuf or MQTT
 * sniffing is ever added here. WHICH ORO attribute id feeds which ISO resource is the
 * attribute-source convention (`settings.iso21423.upstream.attributeSources`, defaults in
 * `config.js:DEFAULT_ATTRIBUTE_SOURCES`). This file translates those ids into canonical keys once,
 * at the queue boundary, and never hardcodes an ORO attribute id anywhere below that.
 */
import path from 'path';
import { loadSync } from 'protobufjs';

import { fromVariant } from '../../lib/util';

/** The queue-side message type ORO publishes attribute updates as (src/server/queues/system.proto). */
const AttributesUpdate = loadSync(path.join(__dirname, '../queues/system.proto'))
  .lookupType('oro.system.AttributesUpdate');

/** Exchange/queue coordinates of ORO's attribute-update fan-out (src/server/queues/messageQueue.js:30-68). */
const EXCHANGE = 'attributes';
const ROUTING_KEY = 'update-values';
const QUEUE = 'iso21423-attributes';

/** Speeds below this magnitude are sensor noise, not motion (m/s and rad/s). */
const MOTION_DEADBAND = 0.02;

/** Canonical keys that change the ISO status; any of them arriving triggers a `publishStatus`. */
const STATUS_KEYS = ['online', 'speedLinear', 'speedAngular', 'batteryPercentage', 'batteryIsCharging'];

/**
 * Maps an accumulated robot state — in CANONICAL keys, already translated out of ORO attribute
 * ids — to the ISO 21423 `states` array.
 *
 * The mode marker comes first (ISO puts the mutually-exclusive MODE_* first). An offline robot is
 * `['OFFLINE']` alone — appending motion or battery states to a robot we cannot hear from would
 * be a lie.
 *
 * @param {Object} s accumulated canonical state: `{ online, paused, speedLinear, speedAngular,
 *   batteryPercentage, batteryIsCharging }` — any field may be undefined
 * @param {number} lowBatteryPercent threshold below which LOW_BATTERY is appended
 * @returns {string[]} ISO operating states, mode first
 */
const mapStatus = (s, lowBatteryPercent) => {
  if (s.online === false) return ['OFFLINE'];

  // TODO(oro-modes): ORO is growing an operating-mode concept. When a robot's mode is observable,
  // add `mode: '<attrId>'` to DEFAULT_ATTRIBUTE_SOURCES and replace the 'MODE_AUTO' constant below
  // with a mapping: teleop session -> MODE_TELEOP, local operator -> MODE_MANUAL, out of service ->
  // MODE_MAINTENANCE, supervised autonomy -> MODE_SEMIAUTO, otherwise MODE_AUTO. Nothing else in
  // this function changes — the mode slot is independent of the motion and battery slots.
  let motion;
  if (s.paused) motion = 'PAUSED';
  else if (s.batteryIsCharging === true) motion = 'CHARGING';
  else if ((s.speedLinear || 0) > MOTION_DEADBAND) motion = 'FORWARD';
  else if ((s.speedLinear || 0) < -MOTION_DEADBAND) motion = 'REVERSE';
  else if ((s.speedAngular || 0) > MOTION_DEADBAND) motion = 'LEFT_TURN';
  else if ((s.speedAngular || 0) < -MOTION_DEADBAND) motion = 'RIGHT_TURN';
  else motion = 'IDLE';

  const states = ['MODE_AUTO', motion];
  if (Number.isFinite(s.batteryPercentage) && s.batteryPercentage < lowBatteryPercent) {
    states.push('LOW_BATTERY');
  }
  return states;
};

class TelemetryTap {
  /**
   * @param {Object} opts
   * @param {Object} opts.workerQueue the InMemoryWorkerQueues instance (may be null in unit tests)
   * @param {(robotId: string) => Object|undefined} opts.handleFor resolves an ORO robot id to its EntityHandle
   * @param {Object} opts.converter a CcsConverter (see ccs.js); `calibrated === false` suppresses odometry
   * @param {number} opts.lowBatteryPercent LOW_BATTERY threshold
   * @param {Object} opts.sources `config.attributeSources` — canonical key -> ORO attribute id
   * @param {boolean} [opts.logging=false]
   */
  constructor({ workerQueue, handleFor, converter, lowBatteryPercent, sources, logging = false }) {
    this._queue = workerQueue;
    this._handleFor = handleFor;
    this._converter = converter;
    this._lowBatteryPercent = lowBatteryPercent;
    this._logging = logging;
    this._state = new Map();   // robotId -> accumulated CANONICAL state
    // Reverse of the source table: ORO attribute id -> canonical key. Attribute ids absent from
    // it are ignored entirely, so the bridge never reacts to an attribute nobody configured.
    this._canonical = new Map(Object.entries(sources).map(([key, attrId]) => [attrId, key]));
  }

  /**
   * Binds `iso21423-attributes` to the `attributes` exchange and subscribes.
   *
   * Safe alongside `derived-attributes`: `InMemoryWorkerQueues.doSend` invokes the callbacks of
   * EVERY queue bound to the exchange+routing key (`src/server/queues/memoryWorkerQueue.js:86-104`).
   */
  start = async () => {
    this._queue.buildExchangeDirect(EXCHANGE);
    await this._queue.bindQueue(EXCHANGE, ROUTING_KEY, QUEUE, { durable: true });
    this._queue.subscribeProto(QUEUE, this.onAttributesUpdate, AttributesUpdate, true);
  };

  /** No-op: `InMemoryWorkerQueues` exposes no unsubscribe. The `handleFor` lookup returns
   *  undefined once the gateway is closed, so late messages are dropped harmlessly. */
  stop = () => {};

  /**
   * Handles one decoded `oro.system.AttributesUpdate`. Publishes battery and odometry when the
   * relevant attributes are present, and status whenever a status-relevant attribute changed.
   *
   * Never throws: a publish failure is logged and swallowed, because this runs on ORO's
   * telemetry hot path and must not break attribute processing for the rest of ingest.
   *
   * @param {{robotId: string, attributes: Object}} update decoded queue message
   */
  onAttributesUpdate = async ({ robotId, attributes }) => {
    const handle = this._handleFor(robotId);
    if (!handle || !attributes) return;

    const state = this._state.get(robotId) || {};
    // Translate ORO attribute ids to canonical keys once, here. Unconfigured ids are dropped.
    const values = {};
    for (const [attrId, attrValue] of Object.entries(attributes)) {
      const key = this._canonical.get(attrId);
      if (key) values[key] = fromVariant(attrValue && attrValue.value);
    }
    if (!Object.keys(values).length) return;
    Object.assign(state, values);
    this._state.set(robotId, state);

    try {
      if ('batteryPercentage' in values || 'batteryVoltage' in values) {
        const battery = {};
        if (Number.isFinite(state.batteryPercentage)) battery.batterySoc = state.batteryPercentage / 100;
        if (Number.isFinite(state.batteryVoltage)) battery.batteryVoltage = state.batteryVoltage;
        if (typeof state.batteryIsCharging === 'boolean') {
          battery.batteryChargingState = state.batteryIsCharging ? 'CHARGING' : 'DISCHARGING';
        }
        await handle.publishBatteryStatus(battery);
      }

      if ('pose' in values && this._converter.calibrated) {
        const pose = state.pose;
        if (pose && Number.isFinite(pose.x) && Number.isFinite(pose.y)) {
          await handle.publishOdometry({
            pose: {
              locationPoint: this._converter.toLocationPoint(pose),
              orientation: this._converter.toOrientation(pose),
            },
            velocity: { linear: state.speedLinear || 0, angular: state.speedAngular || 0 },
          });
        }
      }

      if (STATUS_KEYS.some((k) => k in values)) {
        await handle.publishStatus({ states: mapStatus(state, this._lowBatteryPercent) });
      }
    } catch (err) {
      if (this._logging) console.warn(`ISO 21423 telemetry publish failed for ${robotId}: ${err.message}`);
    }
  };

  /**
   * Sets or clears the bridge-local `paused` flag for a robot and republishes its status.
   * Called by the command executor (see commands.js) — ORO has no pause state of its own.
   */
  setPaused = async (robotId, paused) => {
    const state = this._state.get(robotId) || {};
    state.paused = paused;
    this._state.set(robotId, state);
    const handle = this._handleFor(robotId);
    if (!handle) return;
    try {
      await handle.publishStatus({ states: mapStatus(state, this._lowBatteryPercent) });
    } catch (err) {
      if (this._logging) console.warn(`ISO 21423 pause status publish failed for ${robotId}: ${err.message}`);
    }
  };
}

export { TelemetryTap, mapStatus, MOTION_DEADBAND, EXCHANGE, ROUTING_KEY, QUEUE };
```

**[HUMAN-DECIDED] Every command goes through ORO's Actions framework.** There is no direct
`r/<robotId>/…` publish anywhere in the bridge — not for `move`, not for pause, not for cancel. The
single ingress is:

> `POST {peerClient.url}/api/robots/<robotId>/actions`, header `x-auth-peer-key`,
> body `{ actionId, parameters }`.

What that buys, all verified:

- **Operator locks are enforced.** `isSystemUser` short-circuits the *permission* gates
  (`app/imports/server/lock.js:396`, `:413`) but **not** the lock check — the branch at `lock.js:430`
  has no system-user bypass, and the comparison at `:437` is `robotLock.userId != userId` with
  `userId === 'oro'` (`app/imports/server/rest_api.js:205-208`,
  `app/imports/shared/roles.js:71-89`). A robot locked by a human operator therefore rejects an ISO
  command. Every action the bridge runs is `lock: true` in its template
  (`app/imports/shared/actions.js:180` NavigateTo, `:203` CancelNavGoal; `lock` is a plain
  ActionDefinition field, `app/imports/lib/actions.js:48`, constant at `lock.js:44`).
  **Caveat to document:** locking only engages when the tenant's lock preference is `automatic` or
  `explicit`; the default is `disabled` (`app/imports/lib/lock.js:24-42`). With locking disabled
  nobody is locking anything, including the UI, so this is not an ISO-specific hole.
- **ORO writes the audit log itself**, for successes (`EventLog.logExecutedAction`,
  `app/imports/server/actions.js:1316`) *and* failures (`_logActionFailure` →
  `EVENT_TYPES.ACTION_FAILED`, `lock.js:359-376`; plus the unknown-action case at
  `app/imports/server/rest/actions.js:78-91`). The bridge writes no audit line for anything it
  hands to ORO — see Task 5c for the narrow residue it *does* log.
- Argument resolution and validation (`actions.js:853-947`), the robot-online check
  (`actions.js:1164`), handlebars substitution and the `executionId` all come for free.

Accepted costs, both stated in Global Constraints: one HTTP round trip per command, and the Meteor
app becomes a hard runtime dependency of the ISO command path (telemetry and registration keep
working without it).

**Note the `navGoal` strategy is no longer a bypass.** The original draft had it publish
`ros/nav/goal_to_current_pose` directly over MQTT. It does not need to: ORO exposes exactly that
behaviour as the seeded `CancelNavGoal` ActionDefinition (`nav2d.cancelNavGoal` publishes the very
same topic, `app/imports/server/modules/nav2d.js:59-71`). Routing it through the framework keeps
locks and audit intact, and removes the last direct-MQTT command path from the bridge. The strategy
now means *"use ORO's built-in stop/re-goal actions instead of deployment-specific pause actions"* —
useful when a deployment has not defined `pauseRobot`/`resumeRobot`, with the honest limitation that
it only stops **navigation**, not whatever else the robot was doing. `'action'` remains the default.

**Pose frame.** `NavigateTo` accepts `pose.frameId` and defaults it from the robot's current
localization (`actions.js:1550-1556`), but **the frame is dropped on the wire** — `sendNavGoal`
serializes `ts|x|y|theta` only, and its comment says so verbatim
(`app/imports/server/modules/nav2d.js:82-95`); pose transformation is commented out
(`actions.js:1558-1563`). So the bridge sends ORO-map-frame coordinates and **omits `frameId`
entirely** rather than implying a transform that does not happen. That is exactly what
`CcsConverter.fromCcsPoint` produces.

**Validate arguments in the bridge, not in ORO.** `NavigateTo`'s args are declared `type: 'any'`
(`app/imports/shared/actions.js:190-196`), which short-circuits validation
(`app/imports/shared/actions.js:398-405`) — nothing checks that `pose.x/y/theta` are numbers, and a
malformed pose reaches the robot as the literal string `"…|undefined|undefined|undefined"`. The
bridge's own `MALFORMED_REQUEST` check (below) is therefore load-bearing, not belt-and-braces.

| **5xx**, connection refused, or no response at all | `GENERAL_FAILURE`, plus the `oro-actions-unreachable` diagnostic |

```javascript
    ran,
    has: async (actionId) => (present.includes(actionId) ? { _id: actionId, lock: true } : null),

      ran.push({ robotId, actionId, parameters });
      if (fail) throw Object.assign(new Error(fail.message), fail);
      return { executionId: undefined };
    },
  };
}
```

```javascript
// (Apache-2.0 header)

/**
 * Runs ORO Actions-framework actions from inside ingest. This is the bridge's ONLY command path
 * (pinned decision 8) — no ISO request ever results in a direct `r/<robotId>/…` publish.
 *
 * Mechanism: `POST /api/robots/<robotId>/actions` with the peer key in the `x-auth-peer-key`
 * header (`app/imports/server/rest/actions.js:68`, `:191-197`;
 * `app/imports/server/rest_api.js:197`, `:205-208`). That routes through
 * `LockManager.runRobotAction` (`app/imports/server/lock.js:389`) →
 * `ActionsEngine.runAction` (`app/imports/server/actions.js:501`), so operator locks, argument
 * validation, the robot-online check and ORO's own audit log (both
 * `EventLog.logExecutedAction`, `actions.js:1316`, and `_logActionFailure`, `lock.js:359-376`)
 * all apply to ISO-originated commands exactly as they do to UI-originated ones.
 *
 * `has()` exists so a missing ActionDefinition becomes a clean ISO `ACTION_NOT_IMPLEMENTED`
 * rejection, checked locally, instead of a REST round trip that 404s.
 */

class OroActionRunner {
  /**
   * @param {Object} opts
   * @param {Object} opts.actionDefsColl the `action_defs` collection
   * @param {Object} opts.peerClient the PeerClient singleton
   * @param {(reachable: boolean) => void} [opts.onReachability] called when the app's
   *   reachability changes, for the health signal
   * @param {boolean} [opts.logging=false]
   */
  constructor({ actionDefsColl, peerClient, onReachability = () => {}, logging = false }) {
    this._coll = actionDefsColl;
    this._peer = peerClient;
    this._onReachability = onReachability;
    this._logging = logging;
  }

  /**
   * Looks up an ActionDefinition by id.
   *
   * @param {string} actionId
   * @returns {Promise<{_id: string, type?: string, label?: string, lock?: boolean}|null>}
   */
  has = async (actionId) => this._coll.findOne(
    { _id: actionId }, { projection: { _id: 1, type: 1, label: 1, lock: 1 } });

  /**
   * Executes the action and normalizes ORO's failure shapes, which the REST layer flattens into
   * `[body, status]` with no typed errors (`app/imports/server/rest_api.js:419-439`):
   *
   * - HTTP 404 → `err.notFound = true` (no such ActionDefinition, `rest/actions.js:93`)
   * - HTTP 4xx → `err.rejected = true`, `err.validations` set when the body carried one
   *   (`rest/actions.js:106-114`); the message is ORO's verbatim (`Robot is locked by …`,
   *   `Robot is offline`, `Timeout waiting for robot response`, …)
   * - anything else (5xx, ECONNREFUSED, no response) → neither flag: a transport problem, which
   *   also flips the reachability signal
   *
   * @param {string} robotId
   * @param {string} actionId
   * @param {Object} [parameters]
   * @returns {Promise<{executionId?: string}>} `executionId` is present only for RunScript
   *   actions (`app/imports/server/actions.js:1019-1022`); NavigateTo never has one
   * @throws {Error} flagged as described above
   */
  run = async (robotId, actionId, parameters = {}) => {
    let res;
    try {
      res = await this._peer.runRobotAction({ robotId, actionId, parameters });
    } catch (err) {
      const status = err.response?.status;
      const body = err.response?.data;
      const message = body?.error || body?.message || err.message;
      if (status === 404) {
        this._onReachability(true);
        throw Object.assign(new Error(message), { notFound: true, rejected: true });
      }
      if (status >= 400 && status < 500) {
        this._onReachability(true);
        throw Object.assign(new Error(message), { rejected: true, validations: body?.validations });
      }
      this._onReachability(false);
      throw new Error(message);
    }
    this._onReachability(true);
    if (this._logging) {
      console.log(`ISO 21423 ran ORO action ${actionId} on ${robotId}`, res.data);
    }
    return { executionId: res.data?.executionId };
  };
}

export { OroActionRunner };
```

```javascript
// (Apache-2.0 header)

/**
 * Action execution for the ISO 21423 bridge (`oro_integration.md` §2, "`move`/`pause`/`resume`
 * execution via ORO's existing command path to the robot agent").
 *
 * Every ISO request runs as an ORO ActionDefinition through `OroActionRunner` — there is no direct
 * MQTT publish here, so ISO-originated commands are subject to the same operator locks, argument
 * handling and audit logging as commands issued from the ORO UI (pinned decisions 8 and 9).
 *
 * `move` runs the auto-seeded `NavigateTo` action. `pauseImr`/`resumeImr` follow `pause.strategy`:
 * `'action'` (default) runs the deployment's own `pauseRobot`/`resumeRobot` definitions;
 * `'navGoal'` uses ORO's built-in `CancelNavGoal` plus a re-issue of the stored goal, which stops
 * navigation but nothing else. A cancel of an in-flight `move` runs `CancelNavGoal` too — the
 * Actions framework has no per-execution cancel, and an override goal at the robot's current pose
 * is the honest equivalent (`app/imports/server/modules/nav2d.js:59-71`).
 */

class CommandExecutor {
  /**
   * @param {Object} opts
   * @param {Object} opts.converter a CcsConverter, for CCS → ORO map frame
   * @param {Object} opts.telemetry the TelemetryTap, for the bridge-local `paused` flag
   * @param {(entityUuid: string) => string|undefined} opts.robotIdFor reverse entity→robot lookup
   * @param {Object} opts.actionRunner an OroActionRunner
   * @param {{move: string, cancelNav: string}} opts.actionIds resolved ORO action ids
   * @param {Object} opts.pauseConfig `config.pause`
   * @param {Object} opts.arrival `{ wait(robotId, target, signal) }` — see arrival.js (Task 5b)
   * @param {Object} opts.audit `{ logRejected(entry) }` — see audit.js (Task 5c)
   * @param {boolean} [opts.logging=false]
   */
  constructor({
    converter, telemetry, robotIdFor, actionRunner, actionIds, pauseConfig, arrival, audit,
    logging = false,
  }) {
    this._converter = converter;
    this._telemetry = telemetry;
    this._robotIdFor = robotIdFor;
    this._actions = actionRunner;
    this._actionIds = actionIds;
    this._pause = pauseConfig;
    this._arrival = arrival;
    this._audit = audit;
    this._logging = logging;
    this._lastGoal = new Map();   // robotId -> { x, y, theta } in the ORO map frame
  }

  /** Installs the fleet-wide handlers (replayed onto every current and future IMR, controller ruling R6). */
  register = (gateway) => {
    gateway.onRequest('move', this.handleMove);
    gateway.onRequest('pauseImr', this.handlePause);
    gateway.onRequest('resumeImr', this.handleResume);
  };

  /**
   * Serves ISO `move`: validates the target, converts it from the facility CCS into the ORO map
   * frame, runs the NavigateTo action, and then — in the default `moveCompletion: 'arrival'` mode
   * — waits for the robot's pose to converge inside `toleranceRadius` before reporting SUCCEEDED.
   *
   * Validation here is load-bearing, not defensive: NavigateTo declares its arguments `type: 'any'`
   * (`app/imports/shared/actions.js:190-196`), which short-circuits ORO's own validation
   * (`app/imports/shared/actions.js:398-405`), so a malformed pose would otherwise reach the robot
   * as the literal string "…|undefined|undefined|undefined" (`nav2d.js:87`).
   */
  handleMove = async (action, ctx) => {
    const robotId = this._robotIdFor(ctx.entity.entityUuid);
    if (!robotId) return this._rejectLocally(ctx, 'move', 'GENERAL_FAILURE', 'no ORO robot maps to this entity');

    const props = action.properties || {};
    const loc = props.location;
    if (!loc || !Number.isFinite(loc.x) || !Number.isFinite(loc.y)) {
      return this._rejectLocally(ctx, 'move', 'MALFORMED_REQUEST',
        'move.location must carry numeric x and y', robotId);
    }
    if (!this._converter.calibrated) {
      return this._rejectLocally(ctx, 'move', 'REJECTED',
        `CCS is uncalibrated: ${this._converter.reason}`, robotId);
    }
    if (loc.ccsId && loc.ccsId !== this._converter.ccsId) {
      return this._rejectLocally(ctx, 'move', 'REJECTED',
        `move.location.ccsId ${loc.ccsId} is not this facility's CCS ${this._converter.ccsId}`,
        robotId);
    }
    if (ctx.signal.aborted) return ctx.aborted('OK', 'canceled before dispatch');

    const { x, y } = this._converter.fromCcsPoint(loc);
    const theta = props.orientation ? this._converter.fromCcsYaw(props.orientation.yaw) : 0;
    const goal = { x, y, theta };
    this._lastGoal.set(robotId, goal);

    const failure = await this._runAction(ctx, robotId, this._actionIds.move, { pose: goal });
    if (failure) return failure;

    // 'arrival' (default) waits for pose convergence; 'ack' resolves immediately (Task 5b).
    const outcome = await this._arrival.wait(
      robotId, { x, y, toleranceRadius: props.toleranceRadius }, ctx.signal);
    if (outcome === 'canceled') {
      await this._cancelNav(robotId);
      return ctx.aborted('OK', 'canceled');
    }
    if (outcome === 'timeout') {
      await this._cancelNav(robotId);
      return ctx.aborted('TIMEOUT', 'robot did not reach the goal within the arrival timeout');
    }
    return ctx.succeeded({ oroRobotId: robotId });
  };

  /** Serves ISO `pauseImr` per `pause.strategy`, flagging the robot PAUSED only on success. */
  handlePause = async (action, ctx) => {
    const robotId = this._robotIdFor(ctx.entity.entityUuid);
    if (!robotId) return this._rejectLocally(ctx, 'pauseImr', 'GENERAL_FAILURE', 'no ORO robot maps to this entity');

    const actionId = this._pause.strategy === 'action'
      ? this._pause.pauseActionId
      : this._actionIds.cancelNav;
    const failure = await this._runAction(ctx, robotId, actionId, {}, 'pauseImr');
    if (failure) return failure;

    await this._telemetry.setPaused(robotId, true);
    return ctx.succeeded({ oroRobotId: robotId, oroActionId: actionId });
  };

  /**
   * Serves ISO `resumeImr` per `pause.strategy`. With `'navGoal'` this re-issues the last accepted
   * `move` goal; with no stored goal it succeeds without calling ORO, because the robot is already
   * free to move.
   */
  handleResume = async (action, ctx) => {
    const robotId = this._robotIdFor(ctx.entity.entityUuid);
    if (!robotId) return this._rejectLocally(ctx, 'resumeImr', 'GENERAL_FAILURE', 'no ORO robot maps to this entity');

    if (this._pause.strategy === 'action') {
      const failure = await this._runAction(
        ctx, robotId, this._pause.resumeActionId, {}, 'resumeImr');
      if (failure) return failure;
      await this._telemetry.setPaused(robotId, false);
      return ctx.succeeded({ oroRobotId: robotId, oroActionId: this._pause.resumeActionId });
    }

    const goal = this._lastGoal.get(robotId);
    if (goal) {
      const failure = await this._runAction(
        ctx, robotId, this._actionIds.move, { pose: goal }, 'resumeImr');
      if (failure) return failure;
    }
    await this._telemetry.setPaused(robotId, false);
    return ctx.succeeded({ oroRobotId: robotId, reissuedGoal: Boolean(goal) });
  };

  /**
   * Runs one ORO action, mapping its failure shapes onto ISO reason codes.
   *
   * @returns {Promise<Object|null>} an `ActionResult` to return to the SDK, or `null` when the
   *   action ran successfully and the caller should continue
   */
  _runAction = async (ctx, robotId, actionId, parameters, isoType = 'move') => {
    if (!actionId) {
      return this._rejectLocally(ctx, isoType, 'ACTION_NOT_IMPLEMENTED',
        'no ORO action id is configured for this ISO action', robotId);
    }
    // Checked locally so a deployment gap reads as ACTION_NOT_IMPLEMENTED rather than a 404 that
    // looks like a transport fault, and so the operator gets one actionable log line.
    if (!await this._actions.has(actionId)) {
      console.warn(
        `ISO 21423 bridge: no ActionDefinition with _id "${actionId}" exists, so the ISO `
        + `${isoType} request was rejected. Create it in the \`action_defs\` collection (or via `
        + 'the config API, kind "ActionDefinition") with a `type` from ORO\'s action types — '
        + 'typically "PublishToTopic" or "RunScript" — so the robot can realize it however it '
        + 'likes. See docs/iso21423-bridge.md, "Deployment prerequisites".');
      return this._rejectLocally(ctx, isoType, 'ACTION_NOT_IMPLEMENTED',
        `ORO action "${actionId}" is not configured`, robotId);
    }
    try {
      await this._actions.run(robotId, actionId, parameters);
      return null;
    } catch (err) {
      // ORO logged this failure itself (`lock.js:359-376`), so no bridge-side audit line.
      if (err.notFound) return ctx.aborted('ACTION_NOT_IMPLEMENTED', err.message);
      if (err.validations) return ctx.aborted('MALFORMED_REQUEST', err.message);
      if (err.rejected) return ctx.aborted('REJECTED', err.message);
      return ctx.aborted('GENERAL_FAILURE', err.message);
    }
  };

  /**
   * Rejects a request the bridge refused before ORO ever saw it, and audit-logs it — these are the
   * only rejections ORO cannot log, because no action was ever submitted (Task 5c).
   */
  _rejectLocally = async (ctx, isoType, reason, message, robotId = null) => {
    try {
      await this._audit.logRejected({
        robotId, type: isoType, reason, message, requesterId: ctx.request?.source,
      });
    } catch (err) {
      if (this._logging) console.warn(`ISO 21423 audit log failed: ${err.message}`);
    }
    return ctx.aborted(reason, message);
  };

  /** Best-effort stop after a canceled or timed-out move. Failures are logged, never propagated. */
  _cancelNav = async (robotId) => {
    try {
      await this._actions.run(robotId, this._actionIds.cancelNav, {});
    } catch (err) {
      if (this._logging) console.warn(`ISO 21423 cancel-nav failed for ${robotId}: ${err.message}`);
    }
  };
}

export { CommandExecutor };
```

```javascript
// (Apache-2.0 header)

/**
 * Arrival detection for ISO 21423 `move` (pinned decision 13).
 *
 * ORO has no result channel for navigation — the only real one is
 * `oro.CustomScriptStatusMessage`, ingested by `src/server/modules/customCommands.js:48-111`, and
 * `app/imports/server/rest/actions.js:143` states outright that only RunScript actions report
 * status. So "the robot arrived" has to be observed rather than reported: poll the pose the
 * telemetry tap already tracks until it is inside `toleranceRadius` of the goal.
 *
 * `moveCompletion: 'ack'` opts out and reports SUCCEEDED on the agent's echo ack instead.
 */

/**
 * Builds the arrival waiter for a bridge configuration.
 *
 * @param {Object} config the resolved bridge config (`moveCompletion`, `moveArrival`)
 * @param {{poseOf: (robotId: string) => ({x: number, y: number}|undefined)}} telemetry
 * @returns {{wait: (robotId: string, target: Object, signal: AbortSignal) => Promise<string>}}
 *   `wait` resolves to `'arrived'`, `'timeout'` or `'canceled'` — never rejects
 */
const makeArrivalWaiter = (config, telemetry) => {
  if (config.moveCompletion === 'ack') {
    return { wait: async () => 'arrived' };
  }
  const { timeoutMs, pollMs, defaultToleranceRadius } = config.moveArrival;

  return {
    /**
     * Polls the robot's last known pose until it is within `target.toleranceRadius` metres of
     * `target` (both in the ORO map frame), the deadline passes, or `signal` aborts.
     *
     * A robot that never reports a pose resolves `'timeout'`, not `'arrived'` — silence is not
     * arrival.
     *
     * ponytail: polling, not an event subscription. The tap has no per-robot pose event and one
     * timer per in-flight move is nothing; add a listener on TelemetryTap if concurrent moves
     * ever reach the hundreds.
     */
    wait: (robotId, target, signal) => new Promise((resolve) => {
      const tolerance = Number.isFinite(target.toleranceRadius)
        ? target.toleranceRadius
        : defaultToleranceRadius;
      const deadline = Date.now() + timeoutMs;
      let timer = null;

      const finish = (outcome) => {
        if (timer) clearTimeout(timer);
        signal.removeEventListener('abort', onAbort);
        resolve(outcome);
      };
      const onAbort = () => finish('canceled');

      const poll = () => {
        if (signal.aborted) return finish('canceled');
        const pose = telemetry.poseOf(robotId);
        if (pose && Number.isFinite(pose.x) && Number.isFinite(pose.y)) {
          const dx = pose.x - target.x;
          const dy = pose.y - target.y;
          if (Math.hypot(dx, dy) <= tolerance) return finish('arrived');
        }
        if (Date.now() >= deadline) return finish('timeout');
        timer = setTimeout(poll, pollMs);
        if (timer.unref) timer.unref();
        return undefined;
      };

      if (signal.aborted) return finish('canceled');
      signal.addEventListener('abort', onAbort, { once: true });
      return poll();
    }),
  };
};

export { makeArrivalWaiter };
```

| `move` with no location, or non-numeric `x`/`y` | `MALFORMED_REQUEST` |

| the configured ActionDefinition does not exist (checked locally) | `ACTION_NOT_IMPLEMENTED` |

```javascript
/**
 * Audit logging for ISO 21423 requests the bridge rejects ON ITS OWN (pinned decision 12).
 *
 * Deliberately narrow. Every command the bridge submits runs through ORO's Actions framework, and
 * ORO logs those itself — successes at `app/imports/server/actions.js:1316`, lock/authorization
 * refusals at `app/imports/server/lock.js:359-376`, unknown action ids at
 * `app/imports/server/rest/actions.js:78-91`. Logging them here too would double every line in the
 * audit widget. What ORO cannot log is the request that never reached it: a malformed move, a
 * foreign CCS, an uncalibrated bridge, an unmapped entity, a missing ActionDefinition.
 *
 * Document shape mirrors `LockManager._logActionFailure` (`lock.js:361-371`) so the existing UI
 * renders these rows unchanged, written with a direct insert as `UpstreamModule` already does from
 * ingest (`src/server/modules/upstream.js:964-1006`). The actor is `userId: 'iso21423'` with a
 * configurable `userName` — the UI shows `userName || userEmail || userId`
 * (`app/imports/lib/events.js:387-390`), the same mechanism as upstream's `displayName`
 * (`upstream.js:166`).
 *
 * TODO: third ingest-side writer of this shape (here, `upstream.js:964`, the app's
 * `eventLogger.js`), with the EVENT_* constants duplicated at `upstream.js:125-129`. Extract a
 * shared ingest audit module — or a service both modules call — when a fourth appears.
 */
import { COLLECTIONS } from '../../shared/constants';

/** Mirrors the app's `EVENT_MODULES.ACTION` / `EVENT_TYPES.ACTION_FAILED`
 *  (`app/imports/lib/events.js`), duplicated as `upstream.js:125-126` does. */
const EVENT_MODULE_ACTION = 'action';
const EVENT_TYPE_ACTION_FAILED = 'action.failed';

/** Pseudo-user id for bridge-originated entries, alongside upstream's `'upstream'` (`upstream.js:129`). */
const ISO_USER_ID = 'iso21423';

/**
 * Builds the audit logger for a bridge configuration.
 *
 * @param {Object} config the resolved bridge config (`audit.enabled`, `audit.actorName`)
 * @param {Object} mongo the MongoManager singleton
 * @returns {{logRejected: (entry: Object) => Promise<void>}} a no-op logger when disabled
 */
const makeAuditLogger = (config, mongo) => {
  if (!config.audit || config.audit.enabled === false) {
    return { logRejected: async () => {} };
  }
  const eventLogColl = mongo.getCollection(COLLECTIONS.EVENT_LOG);
  const robotsColl = mongo.getCollection(COLLECTIONS.ROBOTS);
  const actorName = config.audit.actorName || 'ISO 21423 bridge';

  return {
    /**
     * Records one locally-rejected ISO request.
     *
     * @param {Object} entry
     * @param {string|null} entry.robotId ORO robot id, or null when the entity mapped to none
     * @param {string} entry.type ISO action type, e.g. `'move'`
     * @param {string} entry.reason the ISO reason code returned to the requester
     * @param {string} entry.message the human-readable rejection message
     * @param {string} [entry.requesterId] the ISO requester's source uuid
     */
    logRejected: async ({ robotId, type, reason, message, requesterId }) => {

      let robotName = null;
```

### Task 5d: Deployment-prerequisite checks at startup

**Files:**
- Create: `src/server/iso21423/prerequisites.js`
- Modify: `src/server/iso21423/index.js`
- Test: `test/iso21423-prereqs.test.js`

**Interfaces:**
- Consumes: `config.pause` and `config.attributeSources` (Task 1), the `action_defs` and `attr_defs` collections, `OroActionRunner.has` (Task 5).
- Produces: `checkPrerequisites({ config, actionDefsColl, attrDefsColl }): Promise<Array<{ key, ok, message }>>` — one entry per prerequisite, ordered, never throws.

**Why this exists.** ISO 21423 integration is not switch-on-and-go: it needs per-deployment setup
that lives in Mongo and in each robot's own integration, not in `settings.json`. An operator who
enables the bridge without that setup gets a bridge that registers robots, publishes an empty
status and rejects every command — and nothing tells them why. This task makes the gap
**visible and actionable**: one log line per missing prerequisite at startup, and a
`prerequisites` array in `reportHealth()`.

**It never blocks startup.** A missing ActionDefinition is a deployment task, not a config error;
the bridge runs, serves telemetry, and rejects the affected ISO requests with
`ACTION_NOT_IMPLEMENTED` (Task 5) until it is fixed. Same philosophy as the CCS's
`uncalibrated` state (pinned decision 6) and the missing-credential warning (Task 6).

**What is checked** — everything the bridge can verify from Mongo, and nothing it cannot:

| Key | Check | When it fails |
| --- | --- | --- |
| `action.pauseRobot` | an `action_defs` document with `_id === config.pause.pauseActionId` exists | only when `pause.strategy === 'action'` |
| `action.resumeRobot` | same for `config.pause.resumeActionId` | only when `pause.strategy === 'action'` |
| `action.navigateTo` | an `action_defs` document of type `NavigateTo` exists (`config.moveActionId` if set, else the auto-seeded `NavigateTo-000000`) | always |
| `attributes.<key>` | for each `attributeSources` entry, an `attr_defs` document defines that attribute id | always, one entry per source |

`attr_defs` is the attribute-definition collection (`COLLECTIONS.ATTRIBUTE_DEFINITIONS`,
`src/shared/constants.js:33`), keyed by a unique `attributeId`
(`app/imports/lib/attributes.js:32-55`) — the same collection ingest's own `AttributesManager` reads
(`src/server/attributes.js:73`, `:164-169`). Operators populate it through the config API's
`DataSourceDefinition` kind (`app/imports/shared/configAPI.js:74`,
`app/imports/server/configAPI/dataSourceDefinitions.js`).

The attribute check is deliberately weak — it answers "is anything in this deployment configured to
produce this attribute id?", not "does robot X report it". A per-robot check would need the
per-robot vitals config (`AttributesManager.getRobotVitalsConfig`, `src/server/attributes.js`) for
every robot on every startup, and would still be wrong for a robot that is simply offline. The weak
check catches the actual failure mode: a deployment whose battery attribute is called something
else entirely.

```javascript
// (Apache-2.0 header)

/**
 * Startup checks for the ISO 21423 bridge's DEPLOYMENT prerequisites — the setup that lives in
 * Mongo and in each robot's integration rather than in settings.json (pinned decision 15).
 *
 * Two things must be configured per deployment before the bridge is useful:
 *   1. ActionDefinitions the bridge executes: `pauseRobot` and `resumeRobot` (operator-created;
 *      how a robot realizes them is the deployment's choice), plus a `NavigateTo` definition for
 *      `move` (ORO auto-seeds `NavigateTo-000000`, `app/imports/server/actions.js:131-157`).
 *   2. The ORO attributes named by `attributeSources` — the bridge publishes ISO telemetry from
 *      ORO attributes and from nothing else (pinned decision 1), so an attribute nobody produces
 *      is an ISO resource nobody sees.
 *
 * These are reported, never enforced: a missing prerequisite is a deployment task, so the bridge
 * starts anyway, keeps serving telemetry, and rejects only the affected ISO requests. Same
 * philosophy as the uncalibrated-CCS state and the missing-credential warning.
 */

/** ORO's auto-seeded NavigateTo definition id (`app/imports/shared/actions.js` naming scheme). */
const DEFAULT_NAVIGATE_ACTION_ID = 'NavigateTo-000000';

/**
 * Runs every deployment-prerequisite check.
 *
 * Never throws: a failed collection read is reported as a failed check, because a prerequisite
 * report that dies halfway is worse than one that says "could not verify".
 *
 * @param {Object} opts
 * @param {Object} opts.config the resolved bridge config
 * @param {Object} opts.actionDefsColl the `action_defs` collection
 * @param {Object} opts.attrDefsColl the `attr_defs` collection
 * @returns {Promise<Array<{key: string, ok: boolean, message: string}>>} one entry per check,
 *   in a stable order; `message` is actionable prose for the operator
 */
const checkPrerequisites = async ({ config, actionDefsColl, attrDefsColl }) => {
  const results = [];

  const checkActionById = async (key, actionId, how) => {
    try {
      const def = await actionDefsColl.findOne({ _id: actionId }, { projection: { _id: 1 } });
      results.push(def
        ? { key, ok: true, message: `ActionDefinition "${actionId}" is present` }
        : { key, ok: false, message: `ActionDefinition "${actionId}" is missing. ${how}` });
    } catch (err) {
      results.push({ key, ok: false, message: `could not verify "${actionId}": ${err.message}` });
    }
  };

  if (config.pause.strategy === 'action') {
    await checkActionById(
      'action.pauseRobot', config.pause.pauseActionId,
      'Create it in `action_defs` with a `type` from ORO\'s action types (typically '
      + '"PublishToTopic" or "RunScript") so the robot can realize a pause however it likes. '
      + 'Until then the bridge rejects ISO pauseImr with ACTION_NOT_IMPLEMENTED.');
    await checkActionById(
      'action.resumeRobot', config.pause.resumeActionId,
      'Create it in `action_defs` alongside the pause action. Until then the bridge rejects ISO '
      + 'resumeImr with ACTION_NOT_IMPLEMENTED.');
  }

  // `move` needs a NavigateTo definition. ORO auto-seeds one, so a failure here usually means it
  // was deleted or the deployment configured a different id.
  const moveActionId = config.moveActionId || DEFAULT_NAVIGATE_ACTION_ID;
  try {
    const def = await actionDefsColl.findOne(
      config.moveActionId ? { _id: config.moveActionId } : { type: 'NavigateTo' },
      { projection: { _id: 1 } });
    results.push(def
      ? { key: 'action.navigateTo', ok: true, message: `NavigateTo action "${def._id}" is present` }
      : {
        key: 'action.navigateTo',
        ok: false,
        message: `No NavigateTo ActionDefinition found (looked for "${moveActionId}"). ORO seeds `
          + '"NavigateTo-000000" by default; recreate it or set iso21423.upstream.moveActionId. Until then '
          + 'the bridge rejects ISO move with ACTION_NOT_IMPLEMENTED.',
      });
  } catch (err) {
    results.push({
      key: 'action.navigateTo', ok: false,
      message: `could not verify the NavigateTo action: ${err.message}`,
    });
  }

  // One entry per attribute source, in the source table's own order.
  for (const [canonicalKey, attributeId] of Object.entries(config.attributeSources)) {
    const key = `attributes.${canonicalKey}`;
    try {
      const def = await attrDefsColl.findOne({ attributeId }, { projection: { _id: 1 } });
      results.push(def
        ? { key, ok: true, message: `attribute "${attributeId}" is defined` }
        : {
          key, ok: false,
          message: `No attribute definition produces "${attributeId}", so ISO ${canonicalKey} will `
            + 'never be published. Configure the data source on your robots, or point '
            + `iso21423.upstream.attributeSources.${canonicalKey} at the id this deployment uses.`,
        });
    } catch (err) {
      results.push({ key, ok: false, message: `could not verify "${attributeId}": ${err.message}` });
    }
  }

  return results;
};

export { checkPrerequisites, DEFAULT_NAVIGATE_ACTION_ID };
```

- Produces:
  - **ingest** — `writeRosterState(collection, { id, imrfmId, username, imrs }): Promise<void>` from `rosterState.js`, where `imrs` is `[{ robotId, imrUuid }]`. Idempotent (`$set` of the whole document).

- Document written to the new `iso21423_roster` collection:
  ```js
  {
    _id: 'iso21423-bridge',       // config.rosterStateId
    imrfmId: '<uuid>',            // the IMRFM entity uuid
    username: 'iso21423-bridge',  // the mqtt_credentials username whose acls to maintain
    imrs: [{ robotId: 'r1', imrUuid: '<uuid>' }],   // sorted by robotId
    tsUpdated: 1756100000000
  }
  ```

**Why this split ([HUMAN-DECIDED], pinned decision 10).** The IMR uuids are *derived*
(pinned decision 2), so they exist nowhere except in the bridge's memory — the app cannot compute
the ACL topics without them. But every `mqtt_credentials` write, and the password hashing that goes
with it (`app/imports/server/mqttCredentialUtils.js:38-44`), already lives app-side. So the bridge
publishes the derivation as data and the app provisions from it, which is literally what
`oro_integration.md` §2 asks for: "because grants are Mongo documents, re-provisioning as the fleet
changes can be automated by the app".

**The grant matrix** (ND-15). Topics are the SDK's layout `/ISO_21423/v1/<entityType>/<entityUuid>/…`
(`ts-sdk/src/topics/topics.ts:15`). The bridge credential needs read+write+subscribe on its own
IMRFM subtree and on every managed IMR's subtree — write to publish identity/status/telemetry and
request statuses, read+subscribe to receive inbound requests on `…/request/<uuid>`, all under the
same `#` wildcard — plus read+subscribe on the fleet-wide `identity` wildcard, which the SDK
subscribes unconditionally to resolve destination entity types.

Per pinned decision 11, each grant is **three entries** (`acc: 1` read, `acc: 2` write, `acc: 4`
subscribe), not one OR'd `acc: 7`: `app/imports/server/mqttCredentialProvisioner.js:112-115` states
verbatim that combining the `MOSQ_ACL_*` bits "does not work" and duplicates entries for
subscribe+read, while `:71` OR's read|write into `acc: 3`. Emitting one entry per bit is the only
form both existing code paths agree is safe.

**Idempotency.** `provisionIso21423Acls` does **not** diff in JS: Mongo's `$set` on an identical
array is already a no-op write. It reports `'unchanged'` when the stored array deep-equals the
wanted one purely so the observer can skip logging, and `'missing'` when no credential document
matches `username` — mirroring the existing provisioner's read-then-act shape
(`mqttCredentialProvisioner.js:55-58`) while fixing its real gap: `provisionRobotCredentials`
**never updates an existing document's `acls`**, so re-provisioning is a genuinely new capability
here, not a duplicate.

**Credential creation stays out of scope on both sides.** A `mqtt_credentials` document requires a
`password` (schema `app/imports/server/collections.js:33`) and `tsCreated`
(`:60`, required), and the bridge's plaintext password lives in *ingest's* settings, not the app's.
So the provisioner updates an existing document and logs the document to create when it is absent.
ND-15's connect-time self-check then surfaces any remaining gap.

```javascript
// (Apache-2.0 header)

/**
 * Publishes the ISO 21423 bridge's roster state for the app-side ACL provisioner
 * (pinned decision 10, `app/imports/server/iso21423AclProvisioner.js`).
 *
 * The IMR entity uuids are DERIVED from ORO robot ids (see entityUuid.js) and are stored nowhere
 * else, so the app cannot compute the ACL topics without them. This one document is the whole
 * interface between the two services: the bridge owns the derivation, the app owns every
 * `mqtt_credentials` write.
 */

/**
 * Upserts the roster-state document. Idempotent: the whole document is `$set`, so a write with
 * unchanged content is a Mongo no-op and never removes a robot by accident.
 *
 * `imrs` is sorted by `robotId` so the stored document is byte-stable across restarts — the
 * app-side observer then only fires on real changes.
 *
 * @param {Object} collection the `iso21423_roster` collection
 * @param {Object} state
 * @param {string} state.id document `_id` (`config.rosterStateId`)
 * @param {string} state.imrfmId the IMRFM entity uuid
 * @param {string} state.username the `mqtt_credentials` username whose `acls` to maintain
 * @param {Array<{robotId: string, imrUuid: string}>} state.imrs currently registered IMRs
 * @returns {Promise<void>}
 */
const writeRosterState = async (collection, { id, imrfmId, username, imrs }) => {
  const sorted = [...(imrs || [])].sort((a, b) => (a.robotId < b.robotId ? -1 : 1));
  await collection.updateOne(
    { _id: id },
    { $set: { imrfmId, username, imrs: sorted, tsUpdated: Date.now() } },
    { upsert: true });
};

export { writeRosterState };
```

```javascript
/**
 * Broker ACL provisioning for the ISO 21423 bridge credential.
 *
 * The bridge (in the `ingest` service) publishes its roster state — the IMRFM uuid plus each
 * managed robot's DERIVED IMR uuid — into the `iso21423_roster` collection. This module observes
 * that document and keeps the bridge credential's `mqtt_credentials.acls` array in step, so grants
 * are re-provisioned automatically as the fleet changes (ISO 21423 ND-15; see the SDK's
 * `docs/nodejs_design/docs/oro_integration.md` §2).
 *
 * The split exists because the IMR uuids are derived and stored nowhere else, while every
 * `mqtt_credentials` write and the password hashing that goes with it
 * (`mqttCredentialUtils.js:38-44`) belongs on this side.
 *
 * Sibling of `mqttCredentialProvisioner.js`, and deliberately narrower: it maintains the `acls`
 * array of an EXISTING credential and never creates one. The bridge's plaintext password lives in
 * ingest's settings, not the app's, so there is nothing here to hash.
 */
import { Meteor } from 'meteor/meteor';
import { isEqual } from 'lodash';

import { COLLECTIONS } from '../shared/constants';
import { MqttLogins } from './collections';

/** `mosquitto-go-auth` access constants (mirrors `mqttCredentialProvisioner.js:39-42`). */
const MOSQ_ACL_READ = 0x01;
const MOSQ_ACL_WRITE = 0x02;
const MOSQ_ACL_SUBSCRIBE = 0x04;

/** ISO 21423 protocol namespace; must match the SDK's `ROOT_NAMESPACE`. */
const ROOT_NAMESPACE = '/ISO_21423/v1';

const Iso21423Roster = new Mongo.Collection(COLLECTIONS.ISO21423_ROSTER);

/**
 * Emits read + write + subscribe entries for one topic filter.
 *
 * Three separate entries rather than one OR'd `acc`: `mqttCredentialProvisioner.js:112-115`
 * documents that combining the MOSQ_ACL_* bits "does not work" and duplicates entries for
 * subscribe+read, while `:71` OR's read|write into 3. One entry per bit is the only form both
 * paths agree is safe.
 */
const rws = (topic) => [
  { topic, acc: MOSQ_ACL_READ },
  { topic, acc: MOSQ_ACL_WRITE },
  { topic, acc: MOSQ_ACL_SUBSCRIBE },
];

/**
 * The ND-15 grant matrix for a bridge credential, as `mqtt_credentials.acls` entries.
 *
 * Read+write+subscribe on the IMRFM's own subtree and on each managed IMR's subtree (identity,
 * status, telemetry, inbound `request/<uuid>` and outbound `request/<uuid>/status` all live under
 * the same `#`), plus read+subscribe on every entity's retained `identity` topic, which the SDK
 * subscribes unconditionally to resolve destination entity types.
 *
 * Ordering is deterministic (IMRs sorted by uuid) so `provisionIso21423Acls` can compare with
 * `isEqual` and skip no-op writes.
 *
 * @param {{imrfmId: string, imrs: Array<{robotId: string, imrUuid: string}>}} state the roster doc
 * @returns {Array<{topic: string, acc: number}>}
 */
export function aclsFor(state) {
  const uuids = (state.imrs || []).map((i) => i.imrUuid).filter(Boolean).sort();
  return [
    ...rws(`${ROOT_NAMESPACE}/IMRFM/${state.imrfmId}/#`),
    ...uuids.flatMap((uuid) => rws(`${ROOT_NAMESPACE}/IMR/${uuid}/#`)),
    { topic: `${ROOT_NAMESPACE}/+/+/identity`, acc: MOSQ_ACL_READ },
    { topic: `${ROOT_NAMESPACE}/+/+/identity`, acc: MOSQ_ACL_SUBSCRIBE },
  ];
}

/**
 * Brings the bridge credential's `acls` array in line with a roster-state document. Idempotent.
 *
 * @param {Object} state an `iso21423_roster` document
 * @returns {Promise<'updated'|'unchanged'|'missing'>} `'missing'` when the state document is
 *   incomplete or no `mqtt_credentials` document matches its `username` — in the latter case an
 *   actionable warning naming the document to create is logged, and the ISO SDK's connect-time
 *   self-check (ND-15) then surfaces the resulting denial.
 */
export async function provisionIso21423Acls(state) {
  if (!state || !state.imrfmId || !state.username) {
    console.warn('iso21423AclProvisioner: incomplete roster state, leaving grants untouched:',
      JSON.stringify(state));
    return 'missing';
  }
  const doc = await MqttLogins.findOneAsync({ username: state.username });
  if (!doc) {
    console.warn(
      `iso21423AclProvisioner: no mqtt_credentials document for username "${state.username}". `
      + 'The ISO 21423 bridge will be denied by the broker until one exists. Create it with '
      + `{ username: "${state.username}", password: hashPasswordPBKDF2(<the password in ingest's `
      + 'settings.iso21423.upstream.mqtt.password>), superuser: false, acls: [], tsCreated: Date.now() } '
      + '— see docs/iso21423-bridge.md.');
    return 'missing';
  }
  const wanted = aclsFor(state);
  if (isEqual(doc.acls, wanted)) return 'unchanged';
  await MqttLogins.updateAsync({ username: state.username }, { $set: { acls: wanted } });
  console.log(
    `iso21423AclProvisioner: updated ACLs for "${state.username}" `
    + `(${(state.imrs || []).length} IMRs, ${wanted.length} entries)`);
  return 'updated';
}

/**
 * Starts observing `iso21423_roster` and re-provisions on every change.
 *
 * Call once from `server/main.js` startup, next to `seedMasterCredentials()`. Unlike the
 * publication-scoped observers in `status.js:84-117` and `usersManager.js:102-137` this one lives
 * for the process lifetime, so it takes no `onStop`. `added` and `changed` are handled identically
 * — the provisioner re-reads the full document rather than trusting the changed-fields delta, the
 * asymmetry `usersManager.js:118-129` warns about. `removed` is deliberately ignored: dropping the
 * state document should not silently revoke a running bridge's grants.
 *
 * A regular collection needs no `disableOplog` (the `pollingIntervalMs` workaround in
 * `status.js:86-91` is only for cursors over Mongo *views*).
 */
export function startIso21423AclProvisioner() {
  const reprovision = async (id) => {
    try {
      const state = await Iso21423Roster.findOneAsync({ _id: id });
      if (state) await provisionIso21423Acls(state);
    } catch (e) {
      console.error(`iso21423AclProvisioner: error re-provisioning for ${id}: ${e}`);
    }
  };
  Iso21423Roster.find({}).observeChangesAsync({
    added: (id) => reprovision(id),
    changed: (id) => reprovision(id),
    // removed: intentionally not handled — see the doc comment.
  });
  console.log('iso21423AclProvisioner: observing iso21423_roster for ACL changes');
}
```

     just to produce that alarm would add a settings dependency for no behavioural gain.
9. **Audit logging** — ORO logs every ISO command itself, in the existing audit-log widget:
   successes via `EventLog.logExecutedAction` (`app/imports/server/actions.js:1316`), lock and
   other refusals via `_logActionFailure` (`app/imports/server/lock.js:359-376`). The bridge adds
   lines only for requests it rejected before submitting an action — malformed pose, foreign CCS,
   uncalibrated bridge, unmapped entity, missing ActionDefinition — as `action.failed` rows with
   `source: iso21423` and the ISO requester's uuid. `audit.actorName` renames the bridge actor
   exactly as `upstream.displayName` does.
10. **Known limitations**, each with its citation:
   - **Pause/resume with `strategy: 'navGoal'` only stops navigation.** It runs ORO's
     `CancelNavGoal` action, which overrides the goal with the robot's current pose
     (`app/imports/server/modules/nav2d.js:59-71`); a non-navigation activity is neither suspended
     nor resumed. Define `pauseRobot`/`resumeRobot` for a real pause.
   - **Cancelling an ISO request cancels navigation, not "execution N".** ORO's Actions framework
     has no per-execution cancel — no REST route, no Meteor method
     (`app/imports/server/actions.js:88-91`), and `executionId` exists only for `RunScript`
     (`actions.js:1019-1022`). The bridge runs `CancelNavGoal`, which is what ORO's own UI does.
   - **`move` arrival is observed, not reported.** The REST call returns a hardcoded
     `status: 'started'` (`app/imports/server/rest/actions.js:117-127`) and the status route
     answers *"only status for actions of type RunScript is implemented"* (`:143`), so arrival is
     inferred from the pose attribute converging inside `toleranceRadius`. Accuracy depends on
     ORO's pose rate (~1 Hz by default, `ingest/src/server/modules/localization.js:97-99`) and on
     `moveArrival.timeoutMs`. `moveCompletion: 'ack'` reverts to "the command was accepted".
   - **`NavigateTo` ignores frames.** `pose.frameId` is accepted and defaulted but dropped on the
     wire, and pose transformation is not implemented (`nav2d.js:82-95`,
     `app/imports/server/actions.js:1558-1563`), so the bridge sends ORO-map-frame coordinates and
     omits `frameId`. A multi-map facility needs ORO-side work before ISO moves can target another
     map.
   - **Odometry rate is ORO's attribute rate**, not ISO's 30 Hz ceiling, and by design: the bridge
     reads only ORO attributes. Raise ORO's pose rate if faster ISO odometry is needed.
   - **No `dock`/`undock`.** ORO has no docking command; the bridge does not advertise them in
     `accepts`, so the SDK answers with `ACTION_NOT_IMPLEMENTED`.
   - **No `onDispatch` policy**, so `destination: ""` requests are rejected (ND-12).
   - **Robot identity is thin.** ORO robot documents carry no model, serial number or footprint
     (`app/imports/lib/collections.js:36-67`), so the IMR identity `details` carries only name,
     hostname, variant and agent version.
   - **Fleet membership is an explicit id list by default** (`robots.mode: 'list'`); ORO has no
     robot tags yet.
   - **Every online robot reports `MODE_AUTO`** — ORO has no operating-mode concept yet.
11. **Rollout** — 7 steps: (a) set `iso21423_upstream_enabled = true` and re-run
    `scripts/generate-settings.sh`, (b) create the broker credential (§5), (c) satisfy the
    deployment prerequisites (§4) — the `pauseRobot`/`resumeRobot` ActionDefinitions (or set
    `pause.strategy: 'navGoal'`) and the data-source attributes, (d) add `imrfmId`,
    `uuidNamespace`, `ccs` and `mqtt` to the deployment's settings (the Secret in k8s), (e) restart
    ingest and confirm `ISO 21423 bridge is ON` in its log **with no prerequisite warnings**, plus
    `iso21423AclProvisioner: updated ACLs for …` in the **app's** log, (f) verify a retained
    `/ISO_21423/v1/IMRFM/<id>/identity`, (g) issue one ISO `move` and confirm it appears in the
    audit log. Include the `mosquitto_sub -t '/ISO_21423/v1/#' -v` check and the `iso21423_roster`
    document as the thing to inspect when ACLs look stale.
12. **Rollback** — set `enabled: false` and restart. Note that retained ISO topics survive: clear
    them with `mosquitto_pub -r -n -t <topic>` per topic, or leave them for the SDK's janitor. The
    `iso21423_roster` document and the credential's `acls` also survive; delete the document to
    stop the app-side provisioner reacting to it. Any `pauseRobot`/`resumeRobot` ActionDefinitions
    stay too — they are ordinary ORO actions and remain usable from the UI.

## Out of scope for this plan

- **Plan 3 — Examples + e2e:** `examples/imr-simulator`, `examples/imrfm-gateway-template`,
  `examples/fleet-observer`, `examples/facility-sandbox`, and the `ScenarioRunner`
  conformance/interop harness against real brokers (`testing_strategy.md` §3–4,
  `deliverables.md`), all in the `iso21423` repo. This plan's Task 7 suite is broker-free by
  design.
- **Real-broker reconnect/LWT e2e for the bridge** — verifying that the bridge's `LOST_CONNECTION`
  will fires against a real Mosquitto, that its session resumes with `cleanSession: false`, and
  that a denied ACL surfaces as `AuthorizationDenied`. `MemoryBroker` simulates the will and
  `denySubscribe`, but not a genuine TCP drop or `mosquitto-go-auth`'s actual ACL evaluation.
  **Candidate to pull forward from Plan 3**: the `facility-sandbox` compose file already stands up
  an ACL-configured Mosquitto, and ORO ships one at `mqtt/docker-compose.yml` with the real
  `mosquitto-go-auth` plugin and the `mqtt_credentials` Mongo backend — the cheapest place to prove
  pinned decision 11's ACL entry shape is actually accepted by the plugin.
- **A `FleetBackend` package boundary.** `deliverables.md` sketches `FleetBackend` as an interface
  with `connect()`/`listRobots()`/telemetry-stream/`executeMove` methods, and Plan 3's
  `imrfm-gateway-template` will ship it with a mock implementation. This plan implements the same
  *seam* — roster, telemetry tap, command executor — as focused ORO-specific files rather than
  one interface with a single implementation. If the template's interface later stabilizes, those
  files are its natural implementation; extracting them behind it is a mechanical change.
- **A shared ingest-side audit module.** `audit.js`, `UpstreamModule._writeExecutedActionEvent`
  (`src/server/modules/upstream.js:964-1006`) and the app's `EventLog.logExecutedAction` are three
  implementations of one document shape, with the `EVENT_*` constants duplicated in ingest
  (`upstream.js:125-129`). A `TODO:` marks it; extraction waits for a fourth writer.
- **A real per-execution cancel in ORO's Actions framework.** There is none today — no REST route,
  no Meteor method (`app/imports/server/actions.js:88-91`), and `executionId` exists only for
  `RunScript` (`actions.js:1019-1022`), so the bridge's `cancelRequest` runs `CancelNavGoal`, an
  override goal at the robot's current pose. `nav2d.js:59-66` says in its own comment that
  "other possible implementations … include actually cancelling a navigation goal given its ID".
  That is an ORO-side improvement with its own ticket.
- **Frame-aware navigation goals.** `NavigateTo` accepts a `pose.frameId` but drops it
  (`app/imports/server/modules/nav2d.js:82-95`) and the pose transformation is commented out
  (`actions.js:1558-1563`). Until ORO fixes that, ISO moves target the robot's current map only.
- **Waking up `spatial_transformations`** as the Mongo home for CCS reference points, and
  **tag-based fleet selection** (`TODO(oro-tags)`) and **ORO operating modes** (`TODO(oro-modes)`) —
  each an ORO-side change with its own ticket. The bridge has the seam ready for all three.
- **New robot identity fields.** ORO robot documents have no model, serial number or footprint;
  adding them (and surfacing them in the ISO identity and in `disabledCapabilities`) is an ORO
  product change, not a bridge change.
- **`dock`/`undock`, `globalPath`/`globalPlan`/`localTrajectory` publication, and ND-12 dispatch.**
  ORO has no docking command, no planned-path publication that maps onto NURBS or waypoint plans,
  and no fleet-scheduling policy for empty-destination requests.
- **Fixing the adjacent ORO bugs the exploration surfaced.** `src/server/mqtt.js:744`
  (`login?.brokerId | this.defaultBrokerId` — a bitwise `|` where `||` was meant),
  `src/server/model/robot.js:44` and `:64` (missing `await`),
  `app/imports/server/mqttCredentialProvisioner.js:71` vs `:112-115` (contradictory ACL bitmask
  handling), `src/server/mapsStorage.js:340` (unbound `entity`), and
  `app/imports/lib/collections.js:849-850` (exports of undefined identifiers). None block this
