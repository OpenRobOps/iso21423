## What `/mqtt_config` turned out to be, and why it shaped Gate 1

`POST /mqtt_config` (`app/imports/server/http_apis.js:139` → handler `:57-137`) is ORO's robot
bootstrap: a robot posts `{ apiKey, robotId, hostname?, agentVersion? }`, the handler checks the
apiKey against the **fleet-wide** `Meteor.settings.robotApiKeys` array (`:73-81`, generated by
`terraform/main.tf:43-46`), **creates the robot document if it does not exist** (`:86-95`), lazily
provisions `mqtt_credentials` with an ACL of `r/<robotId>/#` (`mqttCredentialProvisioner.js:54-78`),
and returns `{ hostname, port, protocol, websocket_port, websocket_protocol, username, password }`
(`:125-136`). The credential is stable — it stores both a PBKDF2 hash for the broker and an
AES-encrypted copy so the plaintext can be handed back on every call.

Two findings decided the design:

1. **There is no approval anywhere.** No pending state, no allow-list, no quota, no rate limit.
   Anyone holding a `robotApiKeys` value can create arbitrarily many robots with arbitrary ids. The
   only brake is `mqtt_credentials.suspended`, a manual DB edit with no UI or API
   (`app/imports/server/collections.js:52-56`). And the handler carries a standing TODO at
   `:84-85`: *"In the future this could be configurable; ie. robots not to be added
   automatically"*. The human's "onboarding is NOT automatic" requirement is literally that TODO,
   for the ISO path.
2. **`/mqtt_config` is the *only* production path a robot document is born.** `Robots.insertAsync`
   appears once (`app/imports/server/model/robot.js:54`), called from exactly one place
   (`http_apis.js:89`). There is no robot-creating REST route
   (`app/imports/server/rest/robots.js:221-253` registers two `GET`s) and no `Robot` config-API
   kind (`app/imports/shared/configAPI.js:72-91`).

## The onboarding mechanism I picked

**Two gates, mirroring `/mqtt_config` and then splitting off the part it does wrong.**

- **Gate 1 — `POST /iso_mqtt_config`** (Task 6): a deliberate sibling of `/mqtt_config` in the same
  idiom, same `robotApiKeys` auth, same response shape, ISO-namespace ACLs — and it **does not
  create the robot document**. That single omission is the whole point, and it implements the TODO.
- **Gate 2 — the `IsoRobot` config-API kind** (Task 7): `POST /api/configuration/apply` creates the
  ORO robot document via the existing `Robot.createAsync`; clearing it revokes.

Of the three options the human listed — an HTTP call, a config API endpoint, static config — I took
**both of the first two, one per gate**, and rejected static config outright (a fleet change would
need an ingest restart). The config API won Gate 2 over a bespoke REST route because ORO has no
robot-creating route to extend, while operators are already applying `ActionDefinition` and
`DataSourceDefinition` objects for this integration's other prerequisites. **Not marked
`[HUMAN-INPUT-PENDING]`** — the exploration made it a reasoned pick rather than a coin flip. The one
thing worth a second opinion is whether Gate 1 should exist at all in v1 (open question 2 below).

**And no mapping table.** ORO's `VALID_ID_REGEXP` (`app/imports/shared/constants.js:160-161`) is
`/^[-0-9a-zA-Z_]+$/`, which accepts a canonical UUID verbatim. So an ISO robot's entity uuid **is**
its ORO robot id: no lookup, no cache, no invalidation, no drift. The alternative — a collection
shaped like `upstream_mqtt_credentials` (`upstream.js:203-206`), the only per-robot external-id
precedent in the repo — buys nothing but prettier robot ids. This is the largest simplification in
the plan and it also means the shared `deriveEntityUuid` is used only by Plan 5.

Admission is likewise expressed as *the robot document existing*, with no `approved` flag. The
`robots` collection is already ORO's fleet roster; a second boolean would be a second source of
truth, and ingest already has to poll that collection anyway.

## The command-routing seam I picked

**Ingest subscribes to the agent-bound MQTT topics the app already publishes.** ORO's app publishes
navigation commands to `r/<id>/ros/loc/nav_goal` (`app/imports/server/modules/nav2d.js:82-95`) and
`r/<id>/ros/nav/goal_to_current_pose` (`:69-71`); ingest's `OroMqtt.registerListener` subscribes
`r/+/<subtopic>` on the same broker (`src/server/mqtt.js:357-369`). So `IsoCommandRouter` listens
exactly where a robot agent would and translates to `imrfm.sendRequest(...)`.

**The Meteor app is not modified at all** — which was the human's stated hope and turns out to be
strictly better than an app-side switch: ISO robots inherit ORO's operator locks, argument
validation and audit logging for free, the same property Plan 5's decision 9 secures for the other
direction.

**The decisive argument, supplied by the human at review and now pinned: broker affinity.** Ingest
scales horizontally with one instance per MQTT broker — `OroMqtt` builds one `MqttBroker` per
`settings.mqtt.brokers` entry (`src/server/mqtt.js:311-321`) and resolves a robot's broker at
`getMqttBroker` (`:744-758`). A command published on an agent topic therefore lands on the *correct*
ingest instance implicitly, with no routing logic anywhere. Any app→ingest RPC would have to
reproduce that robot→broker→instance mapping and address the right instance itself — a second copy
of broker affinity, desynchronising the moment a robot changes broker. This is what makes topic
sniffing not merely convenient but the only mechanism that scales without new machinery.

**And it is explicitly framed as a shortcut.** The seam exists to leave ORO's app completely
unchanged while the ISO direction proves itself; it is not the end state. `commands.js` carries a
`TODO(iso-seam)` naming the candidate evolution — an ISO-kind ActionDefinition executor inside
`ActionsEngine`, expressing "this robot speaks ISO" as a first-class transport — and naming why it
is rejected for now: an app-side executor has no broker affinity and would need instance routing
invented for it. Writing that down in the code was a review requirement, so nobody inherits the
shortcut believing it was the design.

Alternatives rejected: an app-side transport branch (touches `nav2d.js`, `actions.js`, the lock
path, and loses affinity) and an ingest→app RPC (none exists, and inherits the same problem).

**Two wire details that would have been silent bugs:**

1. The payload is **not** the four fields `nav2d` builds. `sendNavGoal` uses `publishAsync`
   (`nav2d.js:88`), which routes through `_callbackSend` and **prepends a sequence number**
   (`app/imports/server/mqtt.js:481`), so what arrives is
   `"<seq>|<executionTs>|<x>|<y>|<theta>"`. `parseNavGoal` expects exactly five fields.
2. **The echo is mandatory.** `publishAsync` rejects after 10 s unless an `oro.Echo` arrives on
   `r/<id>/echo` (`app/imports/server/mqtt.js:341-347`), which `ActionsEngine` surfaces as *"Timeout
   waiting for robot response"* (`actions.js:1186-1190`). A real agent echoes; the router
   synthesizes one (`oro.Echo` at `src/shared/oro.proto:252-262`) carrying the payload verbatim,
   sequence prefix included, because that prefix is the correlation key. Without this, every ISO
   `NavigateTo` would appear to fail while the robot moved. The router deliberately **withholds**
   the echo when the goal is unusable (unadmitted robot, malformed payload, uncalibrated CCS), so
   the operator's action fails visibly instead of appearing to succeed.

`cancelNavGoal` needs no echo — it uses plain `publish` with no payload and no callback
(`app/imports/server/mqtt.js:314`). It maps to `cancelRequest` when a `move` is in flight, and
otherwise to a `move` to the robot's current position (see the Q3 resolution below — my original
`pauseImr` guess was wrong).

## The mode switch, and how little it costs

All eight ingest telemetry modules are InOrbit-wire-specific — every subtopic they register is an
agent convention and six decode `oro.proto` (`basics.js:40-41`, `system.js:62-63`,
`customData.js:50-51`, `events.js:49-50`, `diagnostics.js:38-42`, `customCommands.js:34-36`,
`localization.js:118-132`, `upstream.js:56`/`:97-114`). Protocol-agnostic and kept: `MongoManager`,
`InMemoryWorkerQueues`, `AttributesManager`, `DerivedAttributesService`, `PeerClient`, and OroMqtt's
registration/dispatch skeleton.

The switch is therefore one `if` in `main.js` plus **one flag that already exists**:
`OroMqtt` honours `config.odometryEnabled !== false` (`mqtt.js:302`) to drop its unconditional
`r/+/ros/odometry/+` subscription (`:402-404`). No change to `mqtt.js` at all.

I deliberately did **not** use the sibling `noDefaultListeners` flag (`mqtt.js:291-297`), even
though it looks tailor-made: it would also drop the built-in `echo` listener, and the router
*synthesizes* echoes that the app's `publishAsync` depends on. Dropping only `logfiles_update` would
need a third flag; it is harmless dead weight and not worth the change.

The `states.yaml` territory turned out to be a red herring for this plan: no such file exists in the
repo. It is operator-authored `ModuleState` config objects reaching **robot agents** via
`r/<id>/modules/set_state` (`app/imports/server/mqtt.js:628-638`), with the `minRunlevel` gotcha
enforced at `agentManager.js:474-505` — and **ingest never publishes ModuleState at all**. ISO
robots are not ORO agents and run no agentlets, so the whole mechanism is simply out of scope. The
per-deployment lever I did reuse is the same idea one level up: an ingest settings flag.

## The telemetry injection seam

`AttributesManager.saveAttributeValues` (`src/server/attributes.js:267`) — the single funnel every
ORO telemetry module already reaches. It resolves the robot's vitals config, parses by declared
type, persists to `attr_values`, and cascades to status evaluation plus the `attributes` and
`robot-poses` exchanges (`:363-390`). Injecting there makes an ISO robot indistinguishable
downstream, **including to Plan 5's own tap**, which reads the far side of that same exchange — the
integration test pins that contract explicitly.

Rejected `handleSystemUpdates` (`:216`): its source filter at `:227-229` exists to stop InOrbit
system stats overwriting a differently-sourced vital, and would silently drop ISO values for any
attribute a deployment maps from elsewhere. Rejected publishing to the exchange directly: it skips
persistence and status evaluation entirely.

## Naming collision, as requested

`settings.upstream` already exists in ORO — the **InOrbit Intelligence forwarder**
(`ingest/src/server/modules/upstream.js`), which also "forwards our fleet upward". Different
protocol, different subtree (`settings.upstream` vs `settings.iso21423.upstream`), so nothing
breaks, but the word is overloaded in conversation and in logs. The plans give the three things
distinct log prefixes (`ISO 21423 robots`, `ISO 21423 bridge`, `UpstreamModule`) and Plan 4 warns at
boot when the InOrbit forwarder is enabled in ISO mode, where it would forward nothing. No other
collisions: `iso21423.robots` does not clash with the `robots` collection, and ingest has no `mode`
setting today.

## Resolved by the 2026-08-26 review

- **Q1 — `manages` links.** Stays as pinned (decision 7): ORO registers only its own IMRFM entity
  and claims no `manages`. **Accepted.** The SDK's only route to `manages` is
  `registerManagedEntity`, which publishes the managed entity's identity into its namespace
  (`ts-sdk/src/core/client.ts:137-158`) — impossible for a self-registered third-party robot, and
  contrary to D-01's federated model. If a future Annex B reading wants `manages` to also mean
  "this IMRFM commands these IMRs", it can be published without the managed-publication machinery;
  nothing in this plan blocks that.
- **Q2 — does Gate 1 ship?** **Yes, in v1.** The discussion that produced the question still holds
  as rationale and is worth keeping: a third-party robot vendor is unlikely to implement ORO's
  bootstrap HTTP call, so an integrator will often read the credential out of Mongo and configure
  the robot by hand. Gate 1 costs one small file, mirrors an endpoint operators already know, and
  gives a real state a name — "admitted, credentials issued, not yet connected". The 2026-08-26
  review additionally **inverted its onboarding behaviour**: it now 403s unless the robot has
  already been admitted (decision 14), which is what makes the fleet-wide `robotApiKeys` secret
  safe to keep using.
- **Q3 — `cancelNavGoal` fallback.** Resolved against my original guess. `pauseImr` was **wrong**:
  a later `resumeImr` would carry on navigating, which is exactly what the operator asked to stop.
  The fallback is now a `move` to the robot's current position — ORO's own semantics
  (`nav2d.js:60-66`) translated faithfully — using the last odometry `LocationPoint` verbatim in its
  own CCS frame, so no transform runs. The no-odometry edge no-ops with a `cancel-nav-no-pose`
  diagnostic: a robot that has never reported a pose is not navigating, and fabricating a goal is
  the one outcome worse than doing nothing.
- **Q4 — the version string.** `'iso-21423-v1'`, with the suffix **derived** from the SDK's
  `ROOT_NAMESPACE` rather than hardcoded, so a future `/v2` namespace updates it automatically. A
  test asserts the derivation rather than the literal, which is the point.

- **Q5 — one shared `Iso21423Client` or two? RESOLVED: two, by design.** The premise of the question
  was wrong. ORO runs its **own** MQTT broker, and that broker *is* the ISO Robots broker — it is
  where ISO-native robots connect. The Upstream direction is the mirror image: it connects **out** to
  an upstream, facility-owned broker. Two brokers means two clients, necessarily, and there is no
  architectural pressure to merge them. So `broker` moved out of the shared block into each
  direction: `iso21423.robots.broker` defaults to ingest's own config (normally omitted entirely),
  `iso21423.upstream.broker` is explicit and never defaulted. The shared block keeps only
  `uuidNamespace`, `ccs` and `logging`.

  The "two IMRFM identities" worry survives only as a **documented, acceptable edge**: an operator
  *may* point `upstream.broker` at ORO's own broker for a co-located facility, and ORO then appears
  there as two IMRFM entities with two uuids and two Last Wills. That is correct behaviour for two
  independent ISO participants, and Task 9 says so.

- **Q6 — should the bridge check ORO's lock preference? RESOLVED: no.** It stays a documentation note
  in Plan 5. No `preferences` read, no startup warning, no prerequisite check. Locking is a
  tenant-wide policy that applies equally to the UI, so an ISO-specific alarm about it would be
  noise, and adding a settings dependency to produce that alarm buys no behavioural change.

- **SDK distribution — DECIDED, not open.** `file:../../iso21423/ts-sdk` is the development
  baseline in both plans. The switch to a published registry version happens only once the SDK is
  finalized and published; Plan 5's Task 8 Step 5 is the single place that flip lives.
