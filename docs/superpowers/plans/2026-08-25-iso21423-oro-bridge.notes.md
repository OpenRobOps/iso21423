# Plan 5 (ISO Upstream bridge) — writer notes

Plan: `docs/superpowers/plans/2026-08-25-iso21423-oro-bridge.md`
Companion: [Plan 4 — ISO Robots](2026-08-25-iso21423-iso-robots.md) and its notes — the opposite

Sources: `oro_integration.md` §2 (binding), §1 and §3; `deliverables.md`
(`imrfm-gateway-template`); `example_imrfm.md`; `nodejs_api.md` §13 (ND-15); the as-built

Actions framework, audit log and MQTT-credential provisioner, plus `terraform/`, `k8s/` and

**Revision 4 (2026-08-25):** ORO's ISO integration split into two independent directions, and this
plan was renumbered **Plan 5 of 5** ("ISO Upstream Bridge"). Settings restructured: `settings.iso21423`
now holds only what both directions share (`uuidNamespace`, `broker`, `ccs`, `logging`) and this
plan's config moved under `iso21423.upstream.*`, with `robots:{mode,ids}` renamed
`upstream.fleet:{mode,ids}` to free `iso21423.robots` for Plan 4. Three files — `sharedConfig.js`,
`entityUuid.js`, `ccs.js` — are now **built by Plan 4** and consumed here; Tasks 2 and 4 lost their
build steps and gained verify-and-wire steps. Terraform renders both direction flags. See
"Revision 4 changes" below.

**Revision 3 (2026-08-25):** two further owner decisions, which override earlier pins where they
conflict — (1) *all* robot commands go through ORO's Actions framework, including `move`, buying
operator locks and ORO-written audit logging; (2) required ActionDefinitions and data-source
attributes are **deployment prerequisites**, reported at startup, never shipped as bootstrap
defaults. Both are folded in and marked [HUMAN-DECIDED]. See "Revision 3 changes" below.

**Revision 2 (2026-08-25):** the project owner reviewed revision 1 and settled six questions. Their
decisions are folded into the plan and marked **[HUMAN-DECIDED]** in its pinned-decisions section, so
an executor knows not to re-decide them. This notes file now records only *how* each decision was
grounded plus the questions that are genuinely still open. The plan document itself is the
authority.

The plan lives in this repo; **all the code it describes lives in the ORO repo** — mostly
`oro/ingest/`, plus one module and one test in `oro/app/` (Task 6). That split is deliberate (the
plan argues from the SDK design docs, which are here) and is stated in the plan's **Repo** line.

## Revision 4 changes

**A. Renumber and cross-reference.** Retitled to "ISO 21423 ISO Upstream Bridge Implementation Plan
(Plan 5 of 5)" with an execution-order note at the top: Plan 4 ships first, both are independent.
Plans 1 and 2 are untouched (historical, executed).

**B. Settings restructure.** The one behavioural consequence worth flagging: `validateConfig` now
takes the *whole* `settings.iso21423` block rather than just this direction's, merges the shared
keys in via `parseShared`, and returns the same flat object every later task already read — so
Tasks 2–8 needed only the `config.robots` → `config.fleet` rename, not a rewrite. Each direction
keeps its own `enabled` flag, its own `mqtt` credential (they need different ACLs) and its own MQTT
session.

**C. Shared-file ownership.** Plan 4 executes first, so it builds `sharedConfig.js` (Task 1),
`entityUuid.js` (Task 2) and `ccs.js` (Task 3). This plan consumes all three, with an explicit
"if Plan 4 has not been executed, run its Tasks 1–3 first" fallback so it stays standalone-
executable. `ccs.js` now carries **both** conversion directions and Plan 4's test covers the round
trip — that round-trip test is the thing stopping the two halves from drifting, and it is the reason
I refused to let either plan keep its own fit.

**D. One thing I deliberately did NOT unify.** Both directions register an IMRFM entity, and if a
deployment runs both against the same broker with the same `imrfmId` they would fight over one
retained identity topic and one Last Will. The plans keep `imrfmId` per-direction rather than
shared, which makes the collision impossible to hit by accident but also means a deployment running
both presents itself as *two* IMRFMs. See open question 5 below.

## Revision 3 changes

**A. All commands through the Actions framework (pins 8 and 9 rewritten).** The exploration
confirmed the decision is not just possible but strictly better than the draft:

- **Locks really are enforced.** `isSystemUser` short-circuits the *permission* gates
  (`lock.js:396`, `:413`) but the lock branch at `lock.js:430` has **no** system-user guard, and
  `:437` compares `robotLock.userId != userId` with `userId === 'oro'`. So a robot locked by a human
  operator refuses an ISO command. Every action the bridge runs is `lock: true` in its template
  (`app/imports/shared/actions.js:180` NavigateTo, `:203` CancelNavGoal; the field is
  `ACTION_FIELD_RESTRICTED`, `lock.js:44`, schema `app/imports/lib/actions.js:48`).
  **The caveat is in the docs, not a hole:** ORO's lock preference defaults to `disabled`
  (`app/imports/lib/lock.js:24-42`), and when it is disabled nobody is locking anything, the UI
  included.
- **Error shapes.** `runRobotAction` never throws — it *returns* `{ error: <string> }`
  (`lock.js:392`, `:397`, `:405`, `:426`, `:439`, `:446`), which `rest/actions.js:106-114` turns
  into HTTP 400 `{ error, validations? }`; an unknown action id is 404 (`:93`); the REST wrapper
  flattens `[body, status]` with no typed errors (`rest_api.js:419-439`). There is no error code —
  a lock rejection is only distinguishable by matching `"Robot is locked"` / `"Robot must be
  locked"` on the message. That string match is now the pinned mapping, and the message is passed
  through to the ISO requester verbatim so the locking operator's name reaches them.
- **`move` = `NavigateTo-000000`**, `parameters: { pose: { x, y, theta } }`
  (`app/imports/shared/actions.js:175-197`; execution `actions.js:1162-1199`; the sibling REST route
  `rest/navigation.js:72-78` sends exactly this shape). **`frameId` is deliberately omitted**: it is
  accepted and defaulted (`actions.js:1550-1556`) but dropped on the wire — `sendNavGoal` serializes
  `ts|x|y|theta` only and says so in its own comment (`nav2d.js:82-95`) — and pose transformation is
  commented out (`actions.js:1558-1563`). Sending a frame would imply a transform that does not run.
- **Bridge-side validation is load-bearing.** NavigateTo declares both args `type: 'any'`
  (`shared/actions.js:190-196`), which short-circuits validation (`shared/actions.js:398-405`).
  Nothing checks that `pose.x/y/theta` are numbers; a malformed pose reaches the robot as the
  literal string `"…|undefined|undefined|undefined"`. The bridge's own `MALFORMED_REQUEST` check is
  the only guard.
- **No direct MQTT publish remains anywhere in the plan.** The draft's `'navGoal'` pause strategy
  published `ros/nav/goal_to_current_pose` by hand. It does not need to: ORO exposes exactly that as
  the auto-seeded `CancelNavGoal-000000` action (`shared/actions.js:198-210` → `actions.js:1235-1249`
  → `nav2d.cancelNavGoal`, `nav2d.js:59-71`, which publishes that very topic). Routing it through
  the framework costs nothing and keeps locks and audit, so **`'navGoal'` is no longer a bypass** —
  it now means "use ORO's built-in stop/re-goal actions instead of deployment-specific pause
  actions", with the honest limitation that it stops navigation only. Default stays `'action'`.
  This slightly reinterprets the brief (which expected the fallback to remain a bypass and be
  labelled as one); the reinterpretation is strictly safer and answers the brief's own question
  — "check whether any residual direct publish remains" — with "it did, and it is now gone".
- **Cancellation.** The Actions framework has no per-execution cancel: no REST route
  (`rest/actions.js:191-212` has exactly three), no Meteor method (`actions.js:88-91`), and
  `executionId` exists only for `RunScript` (`actions.js:1019-1022`). The honest closest behaviour
  is `CancelNavGoal`, which is what ORO's UI itself uses; `nav2d.js:59-66` even notes in prose that
  a real goal-id cancel would be the better implementation. Pinned as such, with the gap listed in
  "Out of scope" as an ORO-side ticket.
- **Arrival stays the default, and is now *required*.** The REST success body is
  `{ status: 'started', startTs, lastUpdateTs }` with `status` hardcoded (`rest/actions.js:117-127`),
  `NavigateTo` never produces an `executionId` at all, and the status route answers *"only status
  for actions of type RunScript is implemented"* (`:143`, backed by `RobotCustomScript`,
  `collections.js:482-518`, 30-minute TTL). There is no navigation feedback in ORO whatsoever, so
  observing the pose is not a preference — it is the only way to know.

**B. Task 5c survived, drastically shrunk.** With everything going through the framework, ORO logs
successes (`actions.js:1316`), refusals (`lock.js:359-376`) *and* unknown action ids
(`rest/actions.js:78-91`). A bridge-side line for any of those would double every row in the audit
widget. What ORO cannot log is the request that never reached it — malformed move, foreign CCS,
uncalibrated bridge, unmapped entity, missing ActionDefinition. Those are worth auditing (they are
how an operator sees something on the ISO network repeatedly trying to command their robots), so
`audit.js` now exposes a single `logRejected()` writing `action.failed` rows shaped like
`_logActionFailure` (`lock.js:361-371`). ~40 lines. I kept it as its own task rather than folding it
into Task 5 because it is independently reviewable and has its own Mongo-backed tests.

**C. Deployment prerequisites (new pin 14, new Task 5d).** The revision-2 suggestion of a reference
`app/private/bootstrap/ActionDefinition.yaml` is **withdrawn** — what "pause" means depends on each
robot's implementation, so it is deployment setup and can never be a seeded default. Instead
`prerequisites.js` checks, at startup and once only, what the bridge can actually verify from Mongo:
the `pauseRobot`/`resumeRobot` definitions (skipped under `strategy: 'navGoal'`), a `NavigateTo`
definition, and one entry per `attributeSources` id against `attr_defs`
(`app/imports/lib/attributes.js:32-55`, populated via the config API's `DataSourceDefinition` kind,
`app/imports/shared/configAPI.js:74`). One `console.warn` per gap plus a `prerequisites` block in
`reportHealth()`; never blocks startup. The attribute check is deliberately weak — "does anything in
this deployment produce this id" rather than "does robot X report it" — because a per-robot check
would need every robot's vitals config on every boot and would still be wrong for an offline robot.

**D. App dependency surfaced.** Global Constraints now state that the Meteor app must be up for any
ISO command; telemetry, registration and ACL publishing are unaffected. `OroActionRunner` reports
reachability changes through an `onReachability` callback, which emits an `oro-actions-unreachable`
diagnostic and sets `reportHealth().actions = 'unreachable'`.

## What the review settled, and how each was grounded

1. **Robot selection accepted as drafted** (explicit id list, `mode: 'all'` available). A
   `TODO(oro-tags):` now sits at the selector in `config.js` (Task 1) and is cross-referenced from
   pinned decision 4 and the out-of-scope list. Confirmed again during grounding that ORO robot
   documents have no `tags`/labels field (`app/imports/lib/collections.js:36-67`); the undeclared
   `collections` array at `ingest/src/server/model/robot.js:97` is the only fleet-subset-ish field
   and nothing maintains it. Adding `mode: 'tagged'` later is one branch in `config.js` and one in
   `RobotRoster.refresh`'s query builder.

2. **Modes are coming; pin 7 stays interim.** `TODO(oro-modes):` is placed twice — as a blockquote
   at the head of Task 3's state table (with the intended `MODE_TELEOP`/`MODE_MANUAL`/
   `MODE_MAINTENANCE`/`MODE_SEMIAUTO`/`MODE_AUTO` mapping spelled out) and as a code comment at the
   exact line in `mapStatus` where the `'MODE_AUTO'` constant is produced. The mode slot is already
   separate from the motion slot, so nothing else in the table moves when it lands. The rest of the
   table (charging > low-battery ordering, 0.02 dead-band, `LEFT_TURN`/`RIGHT_TURN`, no
   `LOST`-on-stale) is marked [HUMAN-DECIDED] as drafted.

3. **Pause/resume via the Actions framework — the mechanism is pinned, and it is a real one.**
   *(Superseded in scope by revision 3: this path is now used for `move` and cancel as well. The
   grounding below still stands.)* The human's convention checks out. The path:

   > `POST {peerClient.url}/api/robots/<robotId>/actions`, header `x-auth-peer-key`,
   > body `{ actionId, parameters }`.

   Grounding: route table `app/imports/server/rest/actions.js:191-197`, handler `apiActionExecute`
   at `:68`, body schema `:34-38`. `validateApiKey` accepts `x-auth-peer-key` against
   `Meteor.settings.peerKey` (`app/imports/server/rest_api.js:64`, `:197`) and with no
   `x-auth-effective-user-id` resolves the caller to the **system user** (`:207`,
   `app/imports/shared/roles.js:71-82`), which `isSystemUser` (`roles.js:89`) uses to short-circuit
   every authorization gate (`rest_api.js:347`, `:351`, `:394`, `lock.js:396`, `:413`). Ingest
   already holds that key (`settings.peerClient.peerKey`, `ingest/src/server/peer.js:62` — the same
   value as the app's). The handler routes through `LockManager.runRobotAction` (`lock.js:389`) →
   `ActionsEngine.runAction` (`actions.js:501`) → `_executeAction` (`:995`), so argument
   substitution, the online check, the `executionId`, the `custom_script` feedback document **and
   the executed-action audit line** (`actions.js:1316`) all come for free.

   Cost is one new `PeerClient` method (Task 5, Step 3). Note the trap the plan calls out: the
   existing `/peer/*` methods put `peerKey` in the JSON **body** (`peer.js:69`, `:83`, `:98`,
   `:115`) because those handlers read it there; `/api/*` reads a **header**. And do not copy
   `updateRobotMode` (`peer.js:111-117`) — it posts to `/peer/robot/mode`, a handler that does not
   exist anywhere in the app.

   Alternatives rejected, all verified: republishing the action's MQTT transport from ingest means
   re-implementing handlebars substitution (`actions.js:744-800`) and validation (`:853-947`); the
   `/peer/*` surface has exactly two endpoints and neither runs actions (`http_apis.js:164`, `:217`);
   there is no queue collection anything observes (no change streams exist in either repo); ingest
   has no DDP client. So **no `TODO(pause-actions)` fallback marker was needed** — the path is real.

   One important consequence, now in the plan: `pauseRobot`/`resumeRobot` **do not exist** in ORO
   and cannot be auto-seeded under those ids — `_addDefaults` only seeds `<Type>-000000` ids for
   non-template action types (`actions.js:131-157`, `app/imports/shared/actions.js:108`). Operators
   create them in `action_defs` with a `type` from the 13 `ACTION_TYPES`
   (`app/imports/shared/actions.js:31-47`), typically `PublishToTopic` or `RunScript`. The bridge
   checks existence first and answers `ACTION_NOT_IMPLEMENTED` with an actionable log line when
   absent, mirroring the missing-credential pattern. `pause.strategy: 'navGoal'` remains as the
   configured fallback.

4. **Audit logging — the lazy path was already blazed.** *(Superseded by revision 3B: ORO now
   writes the executed-action line for every command, so the bridge logs only its own local
   rejections. The `event_log` shape research below is what `audit.js` still mirrors.)* `UpstreamModule` writes `event_log`
   documents directly from ingest, and Task 5c mirrors `_writeExecutedActionEvent`
   (`ingest/src/server/modules/upstream.js:964-1006`) field for field: `module: 'action'`,
   `eventType: 'action.executed'`, top-level actor/robot/ts with everything else under `eventData`
   (the split the app's store performs at
   `app/imports/server/eventLog/meteorDbEventStore.js:24-41`), arguments merged into
   `eventData.action` because that is where the UI reads them
   (`app/imports/lib/events.js:454`), a `source` field that
   `getEventActionDetails` (`events.js:508-528`) renders as extra rows, and the best-effort robot
   name lookup (`upstream.js:986-992`). The configurable actor is the same trick: upstream uses
   `userId: 'upstream'` (`upstream.js:129`) with `userName` from `upstream.displayName`
   (`upstream.js:166`, `:319`), and the UI shows `userName || userEmail || userId`
   (`events.js:387-390`). The bridge uses `userId: 'iso21423'` with `audit.actorName`.

   One thing the review's framing didn't anticipate, and the plan now handles: **`strategy: 'action'`
   pause/resume must NOT be logged by the bridge**, because the REST path already produces the line
   (`actions.js:1316`). Only actions the bridge executes itself (`move`, and `navGoal` pause/resume)
   get a bridge-written line. Otherwise every pause would appear twice in the audit widget.

   A `TODO:` in `audit.js` notes that this is now the third implementation of one document shape
   (here, `upstream.js:964`, `eventLogger.js:116`) with the `EVENT_*` constants duplicated in ingest
   (`upstream.js:125-129`), and that extraction into a shared module or service waits for a third
   ingest writer.

   **The operator-lock bypass remains**, as accepted. It is now the *first* item in the docs'
   known-limitations section, as a callout blockquote, with the practical guidance that broker ACLs
   are the access control for the ISO surface. Note the asymmetry the plan documents: `move` bypasses
   the lock, but `pause`/`resume` with `strategy: 'action'` go **through** it, because they use the
   REST endpoint (`lock.js:430-451` is not bypassed for system users).

5. **ACL provisioning restructured to option (b).** Task 6 is now two-sided:
   - Bridge writes `iso21423_roster` — `{ _id, imrfmId, username, imrs: [{ robotId, imrUuid }], tsUpdated }` — via `src/server/iso21423/rosterState.js`. `imrs` is sorted so the document is byte-stable and the app-side observer only fires on real changes.
   - App gets `app/imports/server/iso21423AclProvisioner.js` with `aclsFor` / `provisionIso21423Acls` / `startIso21423AclProvisioner`, started from `app/server/main.js:110` next to `seedMasterCredentials()`.

   Grounding for the app side: the collection name goes in `app/imports/shared/constants.js`
   (mirrored into ingest by `ingest/import.sh`, so one edit serves both). The observer mirrors
   `app/imports/server/status.js:84-117` minus the `onStop` (it is process-lifetime, not
   publication-scoped), and heeds the `added`-vs-`changed` asymmetry documented at
   `usersManager.js:118-129` by re-reading the full document rather than trusting the delta. No
   `disableOplog` is needed — that workaround (`status.js:86-91`) is only for cursors over Mongo
   *views*.

   Two schema traps the plan calls out: `tsCreated` is **required** on `mqtt_credentials`
   (`app/imports/server/collections.js:60`), and the existing writers store `expiresAt` as a Number
   while the schema says `Date` (`mqttCredentialProvisioner.js:126`) — a latent mismatch not to
   copy. Also worth knowing: `provisionRobotCredentials` **never** updates an existing document's
   `acls` (`mqttCredentialProvisioner.js:55-58`), so re-provisioning is a genuinely new capability,
   not a duplicate of existing code. Credential *creation* stays out of scope on both sides — the
   bridge's plaintext password lives in ingest's settings, not the app's.

   Tests: app-side tests run under `meteortesting:mocha` and **every file must be imported from
   `app/tests/main.js`** (`:19-42`) or it silently does not run; the plan makes that Step 7's first
   action.

6. **Move completion — Task 5b added, `'arrival'` is the default.** `arrival.js` polls the pose the
   telemetry tap already tracks (a new one-line `TelemetryTap.poseOf`) until it is within
   `toleranceRadius` of the goal, both in the ORO map frame, resolving `'arrived'` / `'timeout'` /
   `'canceled'` and never rejecting. A robot that never reports a pose resolves `'timeout'`, not
   `'arrived'` — silence is not arrival. `moveCompletion: 'ack'` returns a stub waiter that resolves
   immediately, preserving the old echo-ack behaviour. Marked with a `ponytail:` comment: it polls
   rather than subscribing, because the tap has no per-robot pose event and one timer per in-flight
   move is nothing.

7. **Telemetry strengthened to attributes-only, forever.** Pinned decision 1 now says so
   explicitly, gives the reason (`registerListener('ros/odometry/data')` would silently disable the
   built-in speed/distance processing at `ingest/src/server/mqtt.js:522-644`, since that branch is
   an `else if` after the `_listeners` check at `:494`; and a second input path means two sources of
   truth for one pose), and states the accepted cost: odometry arrives at ORO's attribute-write rate
   (~1 Hz for pose by default, `localization.js:97-99`), and the remedy is to raise ORO's pose rate,
   not to add a tap. **The full-rate `registerListener('ros/loc/pose')` fallback suggestion from
   revision 1 of these notes is withdrawn.**

   The corollary is the named **ISO attribute-source convention**: `DEFAULT_ATTRIBUTE_SOURCES` in
   `config.js` maps canonical keys to the real ORO attribute ids
   (`src/shared/attributes.js:39-60`) — `online`→`agentOnline`, `pose`→`pose`,
   `speedLinear`, `speedAngular`, `batteryPercentage`, `batteryVoltage`, `batteryIsCharging` — and
   `settings.iso21423.attributeSources` overrides any key per deployment. `TelemetryTap` translates
   ids to canonical keys **once**, at the queue boundary, and drops attribute ids that are not in
   the table; `mapStatus` and everything downstream sees only canonical keys and never an ORO id.
   Documented in Task 3 and as its own section in Task 8's operator guide.

## A bug this plan fixes on the way past

`ingest/src/main.js:200` calls `iso21423.shutdown()` on the smoke-loaded SDK namespace, but the
SDK's root entry (`ts-sdk/src/index.ts`) exports no `shutdown` — the graceful-close method is
`FleetGateway.close()`. As written, that `await` throws on every SIGTERM whenever the optional
dependency is installed. Task 1 replaces the smoke load with a real module that has a `shutdown()`,
so the line becomes correct rather than being deleted.

## Resolved by the 2026-08-26 closing round

1. **`moveArrival` defaults** — `timeoutMs: 120000`, `pollMs: 500`, `defaultToleranceRadius: 0.5` m
   stand as drafted. They are the plan's tunables, documented in Task 8's operator guide so a
   deployment can adjust them per robot class rather than per code change. The known ceiling is
   recorded in the plan: with pose arriving at ~1 Hz a fast robot can cross the tolerance band
   between samples, which is a reason to widen `defaultToleranceRadius` for that deployment, not a
   reason to change the algorithm.
2. **ORO's lock preference** — stays a **documentation note only**. No `preferences` read, no startup
   warning, no prerequisite check. Locking is tenant-wide policy that applies equally to the UI, so
   an ISO-specific alarm would be noise and the settings dependency buys nothing.
3. **What `pauseRobot` should do per deployment** — remains deliberately unspecified, which is the
   point: it is a deployment prerequisite (pin 14), and what "pause" means depends on each robot's
   implementation. Task 8's docs describe the shape (`PublishToTopic` or `RunScript`, any
   realization) without prescribing one, and Task 5d makes a missing definition a visible, actionable
   startup warning rather than a silent failure. No reference bootstrap file ships, by decision.
4. **`ingest/src/server/mqtt.js:744`** (`|` where `||` was meant) — stays out of scope, listed with
   the other adjacent ORO bugs the exploration surfaced. The bridge does not touch that path; it
   deserves its own ticket.
5. **Two directions, two IMRFM identities — RESOLVED: two clients on two brokers, by design.** The
   premise was wrong. ORO runs its own broker, which is the *ISO Robots* broker; this direction
   connects **out** to an upstream facility-owned broker. Two brokers means two clients necessarily,
   and no merge is wanted. Accordingly `broker` moved out of the shared `iso21423.*` block into each
   direction — `iso21423.robots.broker` defaults to ingest's own, `iso21423.upstream.broker` is
   explicit and never defaulted — leaving `uuidNamespace`, `ccs` and `logging` shared. Pointing
   `upstream.broker` at ORO's own broker remains legal for a co-located facility, in which case ORO
   appears there as two IMRFM entities: correct behaviour for two independent participants, and
   documented as such in Task 8.
6. **SDK distribution — DECIDED, not open.** `file:../../iso21423/ts-sdk` is the development
   baseline. The switch to a published registry version happens only once the SDK is finalized and
   published; Task 8 Step 5 is the single place that flip lives, and nothing should pre-empt it.
