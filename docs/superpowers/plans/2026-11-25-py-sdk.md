# Python ISO 21423 library (`py-sdk`) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A ROS-free Python library that lets a process act as an ISO 21423 IMR (publish its resources, serve requests), behaviourally equivalent to the TS SDK's IMR side.

**Architecture:** Port of `ts-sdk/src` (session, topics, schema, request server, executor, policies, sequence, geometry), restricted to the self-entity IMR role. Thread-based: paho's network thread delivers messages; each admitted request runs in its own worker thread; one `RLock` in the request server guards request bookkeeping. A `Transport` protocol separates the protocol logic from paho, so unit tests use an in-memory `FakeTransport` and integration tests use a real Mosquitto.

**Tech Stack:** Python ≥ 3.10, `paho-mqtt` (1.6.x and 2.x), `jsonschema` ≥ 4.10, pytest, Mosquitto 2 (Docker `eclipse-mosquitto:2`) for integration tests, Node 22 + built `ts-sdk` for the interop test.

**Spec:** `docs/superpowers/specs/2026-11-25-ros2-connector-design.md` (section "1. Python library"). Plan 2 (the `iso21423_ros` connector) follows this plan and consumes its public API.

**TS reference:** every task names the TS file it ports. When this plan is silent on a behaviour, the TS code is the source of truth. Divergences are only the two named in Global Constraints.

## Global Constraints

- Location `py-sdk/` beside `ts-sdk/`; import package `iso21423`; src layout `py-sdk/src/iso21423/`; distribution name in `pyproject.toml` is `iso21423` (PyPI availability is the builder's check, per spec).
- Python floor 3.10 (ROS Humble). No numpy. Runtime deps only `paho-mqtt>=1.6,<3` and `jsonschema>=4.10`.
- Must work with paho 1.6.x and 2.x: on 2.x construct the client with `CallbackAPIVersion.VERSION1` so callback signatures are identical to 1.6.
- No ROS imports anywhere in `py-sdk`.
- Wire constants copied from TS: root namespace `/ISO_21423/v1`; protocol version `1.0`; client id `iso21423-<entityType>-<uuid>`; `clean_session=False`; keepalive 60 s; Last Will on `<entity>/disconnection`, payload `{"states":["LOST_CONNECTION"]}`, QoS 1, retained; Table B.1 QoS/retain/rate as in `ts-sdk/src/topics/resources.ts`.
- Timestamps: UTC, millisecond precision, `Z` suffix, identical to JS `toISOString()` (`2026-11-25T12:34:56.789Z`).
- Canonical cancel action `cancelRequest`; inbound `cancel` normalized (D-02).
- Schema: `py-sdk/src/iso21423/schema/iso21423.schema.json` is a byte-identical copy of `ts-sdk/src/schema/iso21423.schema.json`, enforced by a test (Task 2).
- **Deliberate divergences from TS (both recorded as decisions in Task 10):**
  1. New policy `preempt()`: a new request preempts (cancels) every admitted request, then runs (C.2.2 strategy 2). `queue_replace()` keeps the TS meaning (one active plus one queued slot).
  2. Requests whose details are all `pauseImr`/`resumeImr` bypass admission like `cancelRequest`. They are executed (handler runs) but never marked admitted.
- Library default execution policy stays `parallel()` (D-17); the connector picks `preempt()`.
- The TS SDK fix is out of scope: do not edit anything under `ts-sdk/`.
- Publishing to PyPI is not part of this plan (outward-facing release, done on request). Plan 2 installs the library from this repo until then.

## Review Focus

1. **Broker reconnect mid-request.** A request executing when the connection drops must still reach its terminal status after reconnect, and owned retained topics (identity, status, battery, activeRequestsStatus) are republished. Test: Task 9 `test_reconnect_republishes_and_finishes_request`.
2. **Handler that ignores cancellation.** A handler that never checks `ctx.cancelled` must not wedge the server: other requests are still admitted per policy, and the cancelRequest itself still gets SUCCEEDED. Test: Task 7 `test_cancel_of_uncooperative_handler_still_succeeds_cancel`.
3. **Malformed or foreign inbound payloads.** Invalid JSON, schema-invalid requests, and requests with unknown `format`/major `version` must never reach a handler. Readable `(source, sequenceId)` gets ABORTED/MALFORMED_REQUEST; otherwise a validation warning and the retained topic is cleared. Test: Task 7 `test_malformed_request_rejected_or_warned`.
4. **Retained request replay after restart.** On reconnect with `clean_session=False` the broker redelivers retained `request/<uuid>` topics. Already-terminal ones were cleared (zero-byte), and a duplicate `(source, sequenceId)` within a process is ignored. Test: Task 7 `test_duplicate_request_ignored_and_cleared`; Task 9 `test_terminal_request_retained_topic_cleared`.
5. **Handler exception or thread crash.** A raised exception maps to ABORTED/GENERAL_FAILURE and the request leaves `activeRequestsStatus`. Test: Task 6 `test_handler_exception_aborts_general_failure`.

### Task 6: Action executor

Ports `ts-sdk/src/core/executor.ts`, including `resolveCancelRequest`.

**Files:** Create `py-sdk/src/iso21423/executor.py`. Test: `py-sdk/tests/test_executor.py`.

**Interfaces:**
- Consumes: `IncomingRequest` (Task 5), `BLOCKING_STATES` and `PROTOCOL_VERSION` (Task 1).
- Produces:
  - `@dataclass ActionResult(outcome: Literal["succeeded","aborted"], reason: str|None=None, message: str|None=None, properties: dict|None=None)`.
  - `ActionContext`, with:
    - attributes: `.action: dict` (the detail, with `properties` defaulted to `{}`), `.request: dict`, `.entity`
    - `.cancelled: threading.Event`. For an atomic detail it is a private Event that is never set.
    - `.progress(properties: dict) -> None`, which publishes EXECUTING with merged properties
    - `.succeeded(properties=None) -> ActionResult`
    - `.aborted(reason: str, message: str|None=None) -> ActionResult`
  - `ActionHandler = Callable[[dict, ActionContext], ActionResult]`, a blocking call.
  - `RequestKey = tuple[str, int]`: (original sender uuid, sender's sequenceId).
  - `ActionExecutor`, with:
    - `.register(type, handler, override=False)`, which raises if the type is already registered and `override` is not set
    - `.has_handlers()`
    - `.run(incoming: IncomingRequest, entity) -> None`, which blocks and is called on a worker thread
    - `.cancel(key: RequestKey) -> bool`
  - `resolve_cancel_request(cancel_req: IncomingRequest, executors: list[ActionExecutor]) -> None`.
- Same semantics as TS:
  - **Pre-flight order:** `format` ≠ `ISO-21423` → FORMAT_NOT_SUPPORTED; major version ≠ 1 → VERSION_NOT_SUPPORTED; no handler → ACTION_NOT_IMPLEMENTED; a blocking state in `entity.last_states()` with a non-exempt type → INVALID_IMR_STATE_FOR_ACTION. The exempt types are `cancelRequest`, `pauseImr` and `resumeImr`.
  - **Steps:** consecutive non-blocking details run concurrently, each in its own thread, joined before the next step.
  - **Recoveries:** they run with fresh cancel tracking.
  - **Final status:** the last successful detail skips its explicit SUCCEEDED and relies on the cascade.

    - `.abort_new()`, `.queue_after()`, `.queue_replace()`, `.parallel(max=math.inf)`, `.priority()`: TS semantics exactly
    - `.preempt()`: if anything is admitted, returns `Preempt(all admitted keys)`, else `Accept()`. Its `buffer_limit` is 0.
    - `DEFAULT_EXECUTION_POLICY = policies.parallel()`
  - `RequestServer(session, entity, executor, sequence_counter, get_policy: Callable[[], ExecutionPolicy])`, with `.start()` (subscribes `<entity>/request/+` at QoS 2), `.stop()` and `.serving_count -> int`.
  - The server implements `StatusSink`. It publishes `requestStatus` (QoS 2, retained), then `activeRequestsStatus` (every non-terminal request). On a terminal status it removes the request from the active map and clears the retained `request/<uuid>` topic with a zero-byte payload. It then re-admits buffered requests on a new thread.
- Inbound order, as TS `handleInbound`:
  1. Ignore an empty payload.
  2. Parse and validate. On failure, call `reject_or_warn`.
  3. Run the duplicate check on `(source, sequenceId)`. Duplicates are ignored, and their retained topic is cleared.
  4. Publish RECEIVED.
  5. Normalize legacy `cancel`.
  6. Route by type:
     - If the first detail is `cancelRequest`: call `resolve_cancel_request`, with no admission.
     - **If every detail type is in `CONTROL_TYPES`:** run the executor on a new thread, with no admission. The request is never marked admitted.
     - Otherwise: run the policy and apply its decision. On `Preempt`, call `executor.cancel(key)` on each admitted key before accepting.
- A single `threading.RLock` guards `seen`, the active map, the pending list and status emission. Handlers never run under the lock.
