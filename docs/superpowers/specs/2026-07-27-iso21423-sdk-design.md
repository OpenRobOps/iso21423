# ISO 21423 TypeScript SDK — Design

**Date:** 2026-07-27
**Status:** Draft for review
**Source standard:** ISO/FDIS 21423:2026 — Robotics — Industrial mobile robots — Communications and interoperability (MQTT 3.1.1 + JSON)

## 1. Goals and scope

Build a platform-agnostic TypeScript/Node.js SDK implementing ISO 21423, for use in OpenRobOps and other projects, covering both protocol roles:

- **IMRFM gateway**: publish identity/status/telemetry on behalf of a managed fleet (robots that may not speak ISO 21423 themselves) and accept/execute request messages for them — the managed-entity pattern of B.5.2.4.
- **Consumer/client**: discover third-party entities, subscribe to their resources, and send them requests.

**v1 protocol coverage** ("core + easy extras"):

- All required resources: `identity`, `status`, `batteryStatus`, `odometry`, `request/<uuid>`, `request/<uuid>/status`, `activeRequestsStatus`.
- Typed pass-through publishing for `localTrajectory`, `globalPath` (NURBS), `globalPlan`.
- Full Annex C request/requestStatus state machine with standard actions: `move`, `pauseImr`, `resumeImr`, `cancel`, `dock`, `undock`; vendor-extensible action types.
- Annex B session rules: persistent session, Last Will, keep-alive, per-resource QoS/retain, retained-request cleanup.
- CCS types (Clause 4) and Annex D calibration helpers (least-squares rigid transform fit).

**Out of scope for v1:** `footprint` resource updates, NURBS curve evaluation/sampling utilities, scaffolding for custom entity types (B.7 doors/lifts — the open `entityType` string keeps the door open), any platform-specific code (lives in separate adapter packages).

Not safety-related; the standard itself has no safety requirements.

## 2. Package architecture

One npm package, working name `@openrobops/iso21423`, with subpath exports:

```
@openrobops/iso21423
├── /types      Generated + hand-refined TS types, enums, constants
├── /schema     Annex A JSON Schema + runtime validators (ajv)
├── /topics     Topic builder/parser, per-resource QoS/retain config (Table B.1)
├── /geometry   CCS transforms (Annex D affine fit), point/pose utilities
├── /session    Conformant MQTT session (LWT, persistent, keep-alive, publish rules)
├── /gateway    FleetGateway facade (IMRFM role) + request executor
└── /client     Iso21423Client facade (consumer role) + request sender
```

Dependency rules are strictly downward: `gateway`/`client` → `session` → `topics`/`schema`/`types`; `geometry` depends only on `types`.

External dependencies: `mqtt` (behind an injected `MqttTransport` interface, confined to `/session`), `ajv`, `uuid`. The transport interface makes facades and the state machine testable without a broker.

**Design principle:** every behavioral "shall" in the standard (QoS per topic, retained flags, LWT parameters, status-only-on-change, retained-request cleanup) is enforced by the SDK and not expressible incorrectly through the public API. Domain input (a robot's states, how a move executes) is the caller's responsibility.

## 3. Core data types

Types mirror Annex A schema names 1:1 so the standard remains the documentation.

```typescript
// Identity & capability (Tables 4, 7, A.1–A.4, A.12)
interface EntityIdentity {
  id: Uuid; timestamp: IsoTimestamp;
  entityType: "IMR" | "IMRFM" | string;   // open for B.7 extension entities
  manufacturerName: string;
  iso21423Version?: string;               // "1.0"
  capabilities: Capabilities;
  details: ImrDetails | ImrfmDetails;
}
interface Capabilities {
  provides: ResourceName[];
  accepts: { requests: string[] };        // action type names, vendor-extensible
  manages?: Uuid[]; managedBy?: Uuid;
}

// Status & telemetry (Tables 5, 6, 8, 9, A.5–A.11)
interface EntityStatus {
  entityId: Uuid; timestamp: IsoTimestamp;
  states: OperatingState[];               // mode first, then states by priority
  disabledCapabilities?: Capabilities;
}
type OperatingState = KnownOperatingState | string;  // Table 5 enum + deployment extensions
interface Odometry {
  timestamp: IsoTimestamp;
  pose: { locationPoint: LocationPoint; orientation: Orientation };
  velocity: { linear: number; angular: number };
}
interface LocationPoint { ccsId: Uuid; x: number; y: number; z: number }
interface BatteryStatus {
  timestamp: IsoTimestamp; batterySoc: number;       // 0..1
  batteryChargingState?: ChargingState; batteryHealth?: BatteryHealth;
  batteryTemperature?: number; batteryVoltage?: number; batteryCurrent?: number;
}
// LocalTrajectory, GlobalPath (NurbsCurve), GlobalPlan per Tables A.6–A.11

// Requests (Annex C, Tables C.1–C.7)
interface Request {
  destination: Uuid | "";                 // "" → IMRFM picks the robot
  source: Uuid; sequenceId: number; timestamp: IsoTimestamp;
  priority?: number;                      // 0 high … 255 low, default 100
  atomic?: boolean;
  details: RequestDetail[]; recoveries?: RequestDetail[];
}
interface RequestDetail {
  type: string; version: string; format?: string;    // default "ISO-21423"
  blocking?: boolean;                     // default true
  atomic?: boolean;                       // default false
  properties?: Record<string, unknown>;
}
interface RequestStatus {
  source: Uuid; destination: Uuid; sequenceId: number;
  requestSequenceId: number; timestamp: IsoTimestamp;
  status: RequestState;   // RECEIVED|ACCEPTED|EXECUTING|CANCELED|SUCCEEDED|ABORTED|RECOVERY
  detailStatuses: RequestDetailStatus[]; recoveryStatuses?: RequestDetailStatus[];
}
// RequestDetailStatus: type/version/blocking + status{code, reason?, message?} + properties

// Typed action builders + property types for the standard actions:
//   move({location, orientation?, toleranceRadius?, orientationTolerance?, arrivalTime?})  // orientation: see §3.1
//   pauseImr(), resumeImr(), cancel({source, requestId, actionId?})
//   dock({dockLocation, dockId?, dockActions?, ...}), undock()

// CCS (Clause 4) + geometry helpers (Annex D)
interface Ccs { id: Uuid; name: string; referencePointIds: Uuid[] }
interface ReferencePoint { id: Uuid; name: string; x: number; y: number }
// geometry: fitTransform(localPts, ccsPts): RigidTransform2D   (least-squares fit)
//           applyTransform(t, pose), invertTransform(t)
```

Deliberate choices:

1. **Open enums** (`KnownOperatingState | string`): the standard explicitly allows deployment-specific states, action types, and entity types; closed unions would fight real deployments. Validators warn (not reject) on unknown values.
2. **Validation at the boundary, not in the types**: ajv validators generated from the normative Annex A schema run on ingress (client) and optionally on egress (gateway; on by default outside production). Compile-time correctness via types; wire-level conformance via schema.
3. **Timestamps** are ISO 8601-1 strings on the wire; the SDK provides `now()` helper and accepts `Date` at API boundaries, serializing with millisecond precision (`YYYY-MM-DDThh:mm:ss.fffZ`).

### 3.1 Known FDIS inconsistencies and resolution policy

The FDIS text contradicts itself in places. **Resolution rule: the Annex A JSON schema and Annex B topic details win over clause tables and prose** — they define the wire format. Known cases and the SDK's position:

| Where | Conflict | SDK follows |
|---|---|---|
| Status message | Table 6/8 name the fields `id`/`operatingStates`; the Annex A `entityStatus` schema and all B.5.5 examples use `entityId`/`states` | `entityId` / `states` (schema) |
| Active requests topic | B.2.2 says `activeRequestStatus`; Table B.1, B.5.4 and all examples say `activeRequestsStatus` | `activeRequestsStatus` (topic details) |
| Cancel properties | Table C.4 defines `requestId`; the C.1.1.2.6.4 example uses `"id"` | `requestId` (table; example is malformed) |
| Move properties | The C.1.1.2.5 example includes a target `orientation` that Table C.3 never defines (only `orientationTolerance`) | Accept and emit optional `orientation` — tolerance without a target is meaningless, the example reveals the intent |
| Timestamp decimals | Clause tables write `ss,fffZ` (comma); Annex A schema examples use `ss.fffZ` (dot) | Dot (schema; also what `date-time` format implies). Parser accepts both |
| Empty destination | Table C.1 describes empty-`destination` dispatch, but the schema's UUID pattern rejects `""` | Support `""`; patch the bundled schema with `anyOf: [uuid, const ""]` — here the *table* wins because the schema forecloses a described feature |
| NURBS knots | Table A.9 says `array of int32`; schema says `number` items | `number[]` (schema; real-valued knot vectors are standard NURBS) |

Ingress validation treats the deprecated variants leniently (warn + normalize where unambiguous, e.g. accept `id` for `entityId`); egress always emits the schema-conformant form. The full defect catalogue — including gaps that don't change the SDK's wire behavior (no CCS distribution topic, invalid LWT JSON fragment, undefined "non-interruptible QoS", and more) — lives in `docs/iso-fdis-21423-defects.md` with clause-level citations, and doubles as ISO/TC 299 comment material.

## 4. Session layer

`Iso21423Session` wraps the injected MQTT transport and encodes every normative session rule from Annex B:

- **Connect:** persistent session (`cleanSession: false`, stable client ID derived from entity UUID), keep-alive 60 s, mandatory Last Will — topic `<ns>/<entityType>/<uuid>/disconnection`, QoS 1, retained, payload `{"states": ["LOST_CONNECTION"]}`. The LWT fires only on ungraceful disconnect; on (re)connect the session zero-byte-clears any stale retained `disconnection` message left by a prior crash, and graceful shutdown publishes final states then disconnects cleanly (suppressing the will).
- **Publish:** `session.publish(resource, entityRef, payload)` looks up QoS and retain from the Table B.1 registry — callers never pass QoS. Streaming resources (`odometry`, `localTrajectory`) get a token-bucket rate limiter defaulting to the standard's bounds (0.5–30 Hz odometry, 1–10 Hz localTrajectory). Retained resources (`identity`, `status`, …) publish only when the payload actually changed (deep-equality guard implements the "on change" rule).
- **Subscribe:** typed subscription handles that parse the topic, validate the payload, and emit either a typed message or a `ValidationWarning` event — malformed third-party messages never crash consumers (log-and-continue is the only sane multi-vendor posture).
- **Reconnect:** exponential backoff; on reconnect the session republishes all retained resources it owns (broker may have lost them) and re-establishes subscriptions.

## 5. FleetGateway (IMRFM role)

Three responsibilities:

### 5.1 Entity registry

```typescript
const gateway = await FleetGateway.connect({
  broker, transportOptions,
  imrfm: { id, manufacturerName, details, accepts: [...] },
});
const robot: ImrHandle = gateway.registerImr({
  id, identity: { imrModel, imrSerialNumber, imrFootprint, imrWorkingArea,
                  imrHeight, softwareVersions, ... },
  accepts: ["pauseImr", "resumeImr"],   // requests the robot handles directly
});
robot.publishOdometry({ pose, velocity });
robot.publishStates(["MODE_AUTO", "CHARGING"]);
robot.publishBattery(battery);
robot.publishLocalTrajectory(traj); robot.publishGlobalPath(path); robot.publishGlobalPlan(plan);
robot.updateIdentity(partial);        // republishes identity (retained)
gateway.unregisterImr(id);            // publishes final OFFLINE status, zero-byte-clears the
                                      // robot's retained topics, drops it from `manages`,
                                      // republishes the IMRFM identity
```

The gateway publishes the IMRFM's own identity/status and each managed robot's resources under the robot's namespace (`/ISO_21423/v1/IMR/<imrUuid>/…`), filling `manages`/`managedBy` links automatically (B.5.2.4). Publishers are push-based because adapters are event-driven.

### 5.2 Request executor

The SDK owns the Annex C state machine; the host owns action semantics only.

```typescript
gateway.onRequest("move", handler);                    // per action type
gateway.onRequest("move", handler, { imr: imrUuid });  // per robot override

type ActionHandler = (action: TypedRequestDetail, ctx: ActionContext) => Promise<ActionResult>;
// ctx: { imrId, request, signal: AbortSignal, progress(props): void }
// ActionResult: ctx.succeeded(props?) | ctx.aborted(reason, message?)
```

Executor behavior (all automatic):

- Subscribes to `…/request/+` for the IMRFM and for each managed robot that accepts direct requests.
- Runs `RECEIVED → ACCEPTED → EXECUTING → SUCCEEDED | CANCELED | ABORTED` (+`RECOVERY`) transitions per Figures C.3/C.4, publishing `requestStatus` (QoS 2) on every state change — and only on change.
- Sequences `details`: `blocking: true` details run serially; consecutive non-blocking details run concurrently. `atomic` details are never interrupted (cancel waits for completion); a request with `atomic: true` at the top level rejects cancel for its entire duration.
- On failure or cancel with `recoveries` present: transitions to `RECOVERY`, executes recovery details, preserves all detail/recovery statuses; a failed recovery forces overall `ABORTED`.
- Publishes aggregated `activeRequestsStatus` (retained) as requests start/finish.
- Retained-request cleanup after a terminal state (zero-byte publish, B.5.3) is the **sender's** duty, not the executor's — the standard assigns it to the publisher of the retained request (see §6, and the requester ACL in §8). The gateway additionally runs an optional **janitor** (on by default) that zero-byte-clears requests in its own namespaces that are still retained a configurable grace period after reaching a terminal state — protection against senders that crashed before cleaning up.
- `cancel` actions are resolved by the executor itself: matches `source` + `requestId`, fires the target request's `AbortSignal`; `ABORTED` if the target already completed. Handlers never see `cancel` unless they register an override.
- Automatic rejections with proper reason codes: unknown action → `ACTION_NOT_IMPLEMENTED`, schema failure → `MALFORMED_REQUEST`, version mismatch → `VERSION_NOT_SUPPORTED`, format mismatch → `FORMAT_NOT_SUPPORTED`, handler-declared state guard → `INVALID_IMR_STATE_FOR_ACTION`.

**Concurrency policy** pluggable per entity, mirroring C.2.2: `abort-new` (default), `queue-replace`, `queue-after`, `parallel(max)`, `priority`.

### 5.3 Empty-destination dispatch

A request to the IMRFM with `destination: ""` means "IMRFM picks the robot". Fleet-specific by nature, so it delegates:

```typescript
gateway.onDispatch((request, imrs: ImrHandle[]) => Uuid | null);  // null → REJECTED
```

If no dispatch callback is registered, empty-destination requests are rejected with reason `REJECTED`.

## 6. Iso21423Client (consumer role)

```typescript
const client = await Iso21423Client.connect({ broker, identity? });
// identity optional: pure consumers may connect without publishing an entity;
// sending requests requires a source UUID (identity or explicit sourceId).

// Discovery — watches /ISO_21423/v1/+/+/identity (retained ⇒ instant catalog)
client.discover().on("entity", (e: DiscoveredEntity) => ...);
client.entities();                        // current snapshot, incl. manages/managedBy graph

// Typed subscriptions per entity
const imr = client.entity(imrUuid);
imr.odometry.subscribe(cb);  imr.status.subscribe(cb);  imr.battery.subscribe(cb);
imr.disconnection.subscribe(cb);          // LWT: LOST_CONNECTION events
imr.activeRequests.subscribe(cb);

// Request sending — SDK assigns requestUuid + sequenceId, correlates statuses
const req = client.request(destinationUuid, [ move({ location }), dock({ dockLocation }) ],
                           { priority: 50, recoveries: [...] });
req.on("status", (s: RequestStatus) => ...);
await req.completion();     // resolves SUCCEEDED; rejects RequestFailed(ABORTED|CANCELED)
await req.cancel();         // sends a cancel action targeting this request
```

The request sender implements the sender side of B.5.3: publishes the request (QoS 2, retained) to the destination's `request/<requestUuid>` topic, subscribes to `request/<requestUuid>/status`, tracks the state machine, detects staleness (no `RECEIVED` within a configurable timeout → local `RequestTimeout`), and — on any terminal status — **clears the retained request with a zero-byte publish**, as B.5.3 requires of the request's publisher.

Two robustness details:

- **sequenceId durability:** `source` + `sequenceId` must uniquely identify a request, so a naive in-memory counter that resets on restart can collide with still-retained requests. The SDK derives the counter from a persisted seed (pluggable store, default: file) or, if persistence is unavailable, initializes from epoch milliseconds.
- **Sender identity:** to send requests the client needs a source UUID. Strict conformance favors the client also publishing an `identity` (any `entityType`) so receivers can resolve the source; the SDK supports both `identity` (recommended, enables the full entity behavior including LWT) and bare `sourceId` (observer-plus-requests mode). An identity-less client connects as a plain MQTT observer outside the entity model — the B.4 session rules (LWT, persistent session) apply to entities publishing resources, which it is not.

Subscriptions are lazy (MQTT subscribe on first listener, unsubscribe on last) so a dashboard-style consumer doesn't flood itself with 30 Hz odometry from every robot in the facility.

## 7. Error handling

- **Connection errors:** surfaced as session events (`reconnecting`, `offline`, `restored`); publishers buffer nothing by default (stale telemetry is worse than missing telemetry) except retained resources, which republish on reconnect. Request operations in flight during a disconnect fail fast with `BrokerUnavailable`.
- **Inbound malformed messages:** never throw into user code — `ValidationWarning` events with topic, payload, and ajv errors. Gateway-side malformed *requests* get a proper `MALFORMED_REQUEST` requestStatus reply when a reply is possible.
- **Outbound validation failures** (egress validation on): throw synchronously at the publish call site — a conformance bug in the adapter should fail loudly in development.
- **Handler exceptions** in the executor: caught, mapped to `ABORTED` with reason `GENERAL_FAILURE` and the error message; recoveries then run if specified.
- **Typed error classes:** `Iso21423Error` base → `ValidationError`, `RequestFailed`, `RequestTimeout`, `BrokerUnavailable`, `AuthorizationDenied` (denied subscription or failed publish self-check, see §8), `NotCapableError` (e.g. sending `move` to an entity whose capabilities don't accept it — checked client-side against discovered identity, overridable).

## 8. Security: authentication and topic authorization

The standard is intentionally thin here: Clause 10.1 only recommends ("should") following cyber-security and authentication best practices per IEC 62443 or ISO/IEC 27001. No mechanism is normative and topic authorization is not addressed at all — both are delegated to MQTT and the broker deployment.

**Model assumed by the SDK:**

- **Authentication** is connection-time: TLS server auth plus either MQTT CONNECT username/password or mutual TLS (client certificates), validated by the broker. MQTT 3.1.1 offers nothing richer.
- **Authorization** is broker-side ACLs over topic patterns. The topic layout embeds the entity UUID, so deployments can bind each credential to its namespace:
  - IMR: write `/ISO_21423/v1/IMR/<ownUuid>/#`; read as needed.
  - IMRFM gateway: write its own namespace **plus** `/ISO_21423/v1/IMR/<managedUuid>/#` for every managed robot (required by the B.5.2.4 managed-entity pattern) — these cross-namespace grants must be re-provisioned as the fleet changes.
  - Requester: publish on the target's `request/+`, read on `request/+/status`. Clearing a completed retained request (zero-byte publish, B.5.3) needs the same publish right.
  - The LWT `disconnection` message is published by the broker itself; the graceful-shutdown clear of it is a client publish and needs the grant.

**MQTT 3.1.1 caveat:** brokers cannot signal "publish denied" — unauthorized publishes are silently dropped (a PUBACK may still arrive). Denied *subscriptions* are visible via SUBACK return code 0x80.

**SDK responsibilities (in scope):**

- Full pass-through of TLS/mTLS/credential options to the transport (`transportOptions`).
- Surface SUBACK subscription denials as a typed `AuthorizationDenied` error — never silently-missing data.
- Optional startup **self-check**: subscribe to the entity's own `identity` topic, publish, and verify the echo within a timeout — the only reliable way to detect silent ACL publish drops. On by default for the gateway (which is long-lived and high-blast-radius), opt-in for clients.
- Ship a documented **recommended ACL matrix** (per role, per resource) as part of the SDK docs so deployments configure brokers consistently.

**Out of scope:** broker provisioning and hardening, credential/certificate distribution and rotation, and identity lifecycle — deployment concerns per IEC 62443.

## 9. Testing strategy

### 9.1 Unit

State machine tested exhaustively against Figures C.3/C.4 transition tables (table-driven); topic builder/parser round-trips; schema validators against every example payload in Annexes B and C (extracted into fixtures); geometry fit against Annex D worked examples.

### 9.2 Integration (in-memory transport)

Gateway + client wired through an in-memory `MqttTransport` fake — no broker, no network, millisecond-fast, runs in CI on every commit. The fake implements enough MQTT semantics to be meaningful: topic filter matching (`+`/`#`), retained messages, per-subscription QoS, and scriptable connection drops.

Coverage targets:

- **Full request lifecycles:** happy-path multi-detail requests; cancel mid-execution (including cancel of `atomic` details waiting for completion); recovery execution after abort/cancel, including failed recovery → overall `ABORTED`; blocking vs non-blocking sequencing (consecutive non-blocking details run concurrently); every automatic rejection path (`ACTION_NOT_IMPLEMENTED`, `MALFORMED_REQUEST`, `VERSION_NOT_SUPPORTED`, `FORMAT_NOT_SUPPORTED`, `INVALID_IMR_STATE_FOR_ACTION`).
- **Concurrency policies:** each of `abort-new`, `queue-replace`, `queue-after`, `parallel(max)`, `priority` under interleaved requests from two senders.
- **Managed-entity pattern:** gateway publishing under robot namespaces, `manages`/`managedBy` link correctness, direct-to-robot vs via-IMRFM request routing, empty-destination dispatch (including no-callback → `REJECTED`).
- **Session rules as behavior:** status published only on change; rate limiter clamping; sender-side retained-request cleanup on terminal status; gateway janitor clearing orphaned terminal requests after the grace period.

### 9.3 End-to-end / conformance (real broker)

A docker-compose environment with a real broker (Mosquitto, with a second profile for EMQX to avoid broker-specific accidents), run in CI nightly and on release branches. Scenarios are data-driven specs executed by a `ScenarioRunner`; each asserts observable wire behavior, not SDK internals:

1. **Discovery:** a fresh client receives the full entity catalog instantly from retained identities; a late-joining IMR is discovered without resubscribing.
2. **Session conformance:** killing a gateway's TCP connection (not graceful close) makes the broker publish the LWT — subscribers see `LOST_CONNECTION` on the `disconnection` topic, retained; graceful shutdown clears it. Persistent session: QoS 1/2 messages published while a subscriber is offline are delivered on its reconnect.
3. **Retained semantics:** fresh-subscriber checks — after a request reaches a terminal state, a new subscriber to `request/<uuid>` receives nothing (zero-byte cleanup worked); `activeRequestsStatus` reflects only live requests.
4. **QoS verification:** odometry at QoS 0, status/identity at QoS 1, request/requestStatus at QoS 2, asserted from the receiving client's packet metadata.
5. **Telemetry rates:** odometry and localTrajectory publish rates stay within the Table B.1 bounds under a firehose input.
6. **Request round-trips:** move succeed / abort-with-recovery / cancel, issued concurrently from two independent clients against one gateway.
7. **Security suite (§8):** broker configured with ACLs — denied subscription surfaces `AuthorizationDenied`; a gateway with a missing managed-robot grant is caught by the publish self-check; requester without `request/+` write cannot inject requests.
8. **Resilience:** broker restart mid-scenario — sessions resume, retained resources republished, in-flight requests fail fast with `BrokerUnavailable`.
9. **Tolerance:** third-party messages with unknown fields, unknown operating states, and vendor action types pass through with `ValidationWarning`s, never crashes.

### 9.4 Interop harness

The e2e suite doubles as a conformance harness for *external* implementations: point the `ScenarioRunner` at an existing broker and a target entity UUID (env config) instead of the sandbox, and it runs the observer-side assertions (topic layout, QoS, retained behavior, schema validity, request state-machine ordering) against any third-party IMR/IMRFM. Scenarios are tagged by what they require (`observe-only`, `requires-request-execution`, `requires-connection-control`) so partial runs against production-like systems are possible. This is the tool for vendor onboarding and plug-fests.

## 10. Deliverables: sample projects and templates

Shipped in the SDK monorepo under `examples/`, each independently runnable and copyable as a starting template (plain directories, not published packages). They serve three purposes: living documentation, e2e test actors, and integration starting points.

### 10.1 `examples/imr-simulator` — simulated robot (IMR role)

A standalone process simulating one IMR end-to-end:

- Publishes identity, status, battery (drains/charges), and odometry along simple kinematics in a configurable CCS; docks and charges at a configured station.
- Executes `move` (straight-line motion at `ratedSpeed` toward the target, respecting `toleranceRadius`), `pauseImr`/`resumeImr`, `dock`/`undock`, and cancel.
- Configured via a single YAML file: UUID, footprint, speed, battery curve, initial pose.
- **Failure injection** flags for conformance testing: reject next request with a chosen reason, abort mid-move, freeze telemetry, drop the TCP connection (to exercise LWT), delay status transitions.

Used by the e2e suite as its standard robot; doubles as the reference for anyone implementing the IMR side on a real robot. Internally it reuses the gateway's publisher/executor machinery configured as a standalone self-publishing IMR entity — proving that machinery is entity-generic.

### 10.2 `examples/imrfm-gateway-template` — fleet manager template (IMRFM role)

The template integrators copy to connect a fleet platform:

- Defines a small `FleetBackend` interface — `connect()`, `listRobots()`, telemetry event stream, `executeMove/pause/resume/dock(robotId, …)` — as the single seam between the SDK and any platform.
- Ships with an **in-memory mock backend** (3 scripted robots) implementing that interface, so the template runs out of the box; integrators replace one file.
- Demonstrates the full gateway surface: robot registration/unregistration on backend fleet changes, request handlers delegating to the backend, dispatch callback (nearest-idle-robot strategy as the example), CCS transform usage (backend map frame → facility CCS), TLS/ACL configuration, and the §8 publish self-check.

### 10.3 `examples/fleet-observer` — consumer example (client role)

A terminal dashboard built on `Iso21423Client`: discovers all entities, renders a live table (state, mode, battery, position, active requests), tails `disconnection` events, and offers interactive commands to send `move`/`pauseImr`/`resumeImr`/`cancel` to any entity. The template for monitoring/orchestration integrations, and a handy manual-testing tool against any ISO 21423 network.

### 10.4 `examples/facility-sandbox` — one-command demo environment

Docker-compose tying everything together: Mosquitto (ACL-configured), three `imr-simulator` instances, one `imrfm-gateway-template` with the mock backend, and the `fleet-observer`. `docker compose up` yields a complete working ISO 21423 facility in under a minute — the same environment the §9.3 e2e suite runs against, so the demo and the test bed never drift apart.

## 11. OpenRobOps integration and distribution

The first consumer is OpenRobOps (ORO, `github.com/openrobops`): a fleet management platform where a robot agent publishes protobuf over MQTT to a Mosquitto broker, an `ingest` service processes telemetry into MongoDB, and a Meteor app serves API/UI. These facts constrain the SDK build and shape the first adapter.

### 11.1 Compatibility requirements (hard constraints)

- **Plain-JS CommonJS consumers.** ORO has no TypeScript toolchain (`ingest` is CommonJS run via Babel, Flow annotations). The SDK ships a **dual build** — CJS + ESM via an `exports` map with `require`/`import` conditions — plus bundled `.d.ts` (editor IntelliSense works from plain JS; nothing requires consumers to compile TS).
- **Node ≥ 22** (ORO's runtime baseline), ES2022 output, no top-level await in the CJS entry.
- **`mqtt@^5` as a peer dependency.** Both ORO services already depend on `mqtt@^5.15.0`; peering avoids a second copy and version skew. The `MqttTransport` interface also accepts a caller-constructed client.
- **No native modules**, minimal dependency tree (`ajv`, `uuid`) — ORO ships source-as-is Docker images where dependency weight is felt directly.
- **Apache-2.0**, matching ORO.
- **Topic coexistence:** the standard's namespace (`/ISO_21423/v1/...`, leading slash) is disjoint from ORO's agent topics (`ros/...`), so both traffic classes share one Mosquitto instance without collision.

### 11.2 ORO adapter: bridge module inside `ingest`

Decision: the adapter lives **inside the ingest service** (e.g. `oro/ingest/src/server/iso21423/`), not as a separate service. Rationale: ingest already holds a decoded, real-time robot telemetry stream (the exact input the gateway needs), plus ORO's Mongo access and settings conventions. Accepted trade-off: the bridge's lifecycle couples to ingest; the SDK boundary keeps a later extraction into a sibling service cheap.

Sketch:

- The bridge implements the §10.2 `FleetBackend` seam against ORO internals: robot identity/registration from Mongo robot documents; status/odometry/battery from ingest's telemetry pipeline (tapping the already-decoded protobuf stream before Mongo); `move`/`pause`/`resume` execution via ORO's existing command path to the robot agent.
- **CCS calibration:** facility reference points (UUID + coordinates in both the ORO map frame and the CCS) stored in Mongo settings; the bridge uses `/geometry` to fit the transform and converts all outgoing poses.
- **ACL provisioning:** ORO's broker is Mosquitto + `mosquitto-go-auth` backed by the `mqtt_credentials` collection in the Meteor Mongo. The §8 ACL matrix maps to documents there: the bridge credential gets write on `/ISO_21423/v1/IMRFM/<bridgeUuid>/#` plus `/ISO_21423/v1/IMR/<robotUuid>/#` per managed robot — and because grants are Mongo documents, the §8 "re-provision as the fleet changes" requirement can be automated by the app when robots are added/removed.
- **Configuration:** enabled per deployment via ingest's `settings.json` (bridge UUID, CCS reference points, broker credentials); disabled by default.
- The bridge connects with its **own** MQTT session (the SDK needs its persistent-session + LWT semantics), reusing ORO's broker endpoint and credential conventions rather than ingest's existing connection.

### 11.3 Repository, publishing, releases

- **Source:** new repo **`openrobops/iso21423`** — own release cadence, matching the SDK's platform-agnostic positioning. CI mirrors ORO's conventions: PRs build + test; `vX.Y.Z` tags publish.
- **Registry — phase 1: GitHub Packages** (`npm.pkg.github.com`) under the `@openrobops` scope. Consumers (including `oro/ingest`) add a scope mapping in `.npmrc`; CI installs need a `read:packages` token. Known friction: GitHub Packages requires a token even for public packages.
- **Registry — phase 2 (planned): public npmjs.** Once the API stabilizes (target: 1.0, ideally aligned with the standard leaving FDIS), register the `@openrobops` scope on npmjs.com and publish there with provenance from GitHub Actions. The package name doesn't change, so migration is only a registry switch in consumers' `.npmrc`.
- **Versioning:** semver, `0.x` while the standard is in FDIS (§3.1 inconsistencies may resolve differently in the final IS); `1.0` when the published standard is confirmed. The protocol major (`/v1` topic namespace) is independent of the package version and pinned in `/topics`.

## 12. Open questions / future work

- **MQTT 5 brokers:** the standard cites MQTT 3.1.1; the `MqttTransport` interface leaves room to use MQTT 5 features (proper correlation data) later without API changes.
- **Bridge service** (deployable process wrapping FleetGateway with config + plugin backends) is a natural follow-up product on top of this SDK.
- **FDIS caveat:** this is a Final Draft (voting ends 2026-07-20); field names could still shift before publication. Type generation from the Annex A schema keeps the update cost low.
